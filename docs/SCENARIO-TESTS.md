# Сценарии проверки экономики

Этот документ нужен для проверки распределений, прочности, mint и transfer до реализации Solana-программы.

Сценарии описывают Solana-версию проекта. `$FARE` запускается через pump.fun в паре `FARE/SOL`; проект получает переменный Creator Fee в SOL вместо собственных 4%. Состояние хранится в PDA-аккаунтах, fungible assets — в SPL token accounts, NFT-машины — в Metaplex Core Assets, а network fee оплачивается в SOL. Сценарии конвертации комиссий и stock-токенов подтверждаются после соответствующих SOL-вопросов из `TECHNICAL-QUESTIONS.md`.

## Правило связанных сценариев

Сценарии используют одну общую текущую модель проекта. Если решение в одном сценарии меняется, все остальные сценарии нужно повторно проверить и пересчитать под новое решение. Нельзя считать старые выводы действующими, если они опираются на изменённое правило.

## Базовые условия

- Максимальная прочность машины: `X = 5 дней`.
- `collect_fees` фиксирует поступивший SOL и увеличивает отдельные резервы без swap; `process_fare_swap` и `process_stock_swap` независимо выполняют покупки через Jupiter.
- `calculate_rewards` распределяет расчётный пул, а `claim` только переводит уже рассчитанный доход одной машине.
- Накопленный доход принадлежит NFT и переходит её новому владельцу.
- Свежесминченная NFT не получает доход за время до mint, но может участвовать в ещё не распределённом пуле за отрезки после mint.
- Для примеров используются четыре машины:

| Машина | Вес |
|---|---:|
| A | 1 |
| B | 3 |
| C | 10 |
| D | 30 |

## Группы сценариев

### Зафиксированное правило распределения

Пул распределяется пропорционально времени и весу активных машин. Для каждого временного отрезка определяется его доля от общего периода, затем эта сумма делится между активными машинами по весам. Это сознательно сглаживает резкие изменения и повышает шанс раннего дохода для новых пользователей. Правило будет открыто описано в продуктовой документации.

### Правило остатка пула

Если в vault физически лежит `100`, а расчёт обработал один из четырёх равных часовых отрезков, этому отрезку назначается `25`, а для следующих отрезков остаётся `75`. Физический SPL-баланс всё ещё равен `100`, но `25` уже зарезервированы за машинами первого отрезка и повторно не участвуют в расчёте.

### 1. Распределение

- [x] **D1. Первый claim после расчёта** — `calculate_rewards` заранее фиксирует общий пул и доход на единицу веса; первый `claim` ничего не распределяет заново и выплачивает только выбранную машину.
- [x] **D2. Второй claim** — второй владелец получает только свою заранее рассчитанную долю; доход остальных машин не меняется.
- [x] **D3. Повторный claim одной машины** — повторный claim без новых комиссий выплачивает 0; новые комиссии создают новую выплату.
- [x] **D4. Несколько `collect_fees` до `calculate_rewards`** — все собранные деньги объединяются. В момент расчёта весь текущий пул распределяется по временным отрезкам активности; время отдельных сборов не учитывается.
- [x] **D5. Новые комиссии после `calculate_rewards`** — старый пул больше не пересчитывается; новые деньги распределяются отдельным расчётом по текущим активным машинам.
- [x] **D6. Нет активных машин** — при нулевом общем весе деньги остаются в пуле и не теряются.
- [x] **D7. Округление** — минимальный нераспределимый raw-остаток каждого SPL mint остаётся в соответствующем vault и переходит в следующую серию того же токена.

### 2. Потеря прочности

- [x] **P1. Claim через 2 дня после минта** — `claim` выплачивает рассчитанный доход, но не меняет `activeUntil`; до поломки остаётся 3 дня.
- [x] **P2. Claim после полного истечения 5 дней** — машина получает только рассчитанный доход до `activeUntil`; время после поломки не оплачивается.
- [x] **P3. Claim ровно в момент истечения** — при `protocolTime == activeUntil` машина уже сломана; Unix timestamp берётся из Solana `Clock` sysvar, а доход начисляется только за `[activeFrom, activeUntil)`.
- [x] **P4. Машина ломается между двумя claim** — событие `EXPIRE` исключает её из активного веса; следующий `claim` использует сохранённую конечную границу и не начисляет доход после `activeUntil`.
- [x] **P5. Одновременно ломаются несколько машин** — каждая поломка является отдельным событием и отдельным шагом batch-лимита, даже при одинаковой секунде. Между событиями с одинаковым временем доход равен нулю, но каждая NFT отдельно исключается из активного веса. При равном времени используется порядок добавления, а batch-курсор хранит `timestamp + eventNumber`.
- [x] **P6. Большая очередь сломанных машин** — события хранятся в min-heap PDA по `timestamp + eventNumber`. `calculate_rewards` обрабатывает максимум 20 событий и продолжает следующей транзакцией. Backend передаёт необходимые machine PDA; 9000 событий обрабатываются 450 последовательными полными batch. Перед mainnet лимит подтверждается Solana compute/account тестом и при необходимости только уменьшается.

### 3. Ремонт

- [x] **R1. Ремонт до поломки** — если осталось 2 часа из 5 дней, стоимость ремонта считается за недостающие 4 дня 22 часа. Старая запись о поломке через 2 часа удаляется/делается неактуальной, а в очередь добавляется новая запись о поломке через 5 дней после ремонта.
- [x] **R2. Ремонт после поломки** — при обработке repair-события программа закрывает старый период в PDA машины и добавляет его доход в `claimable`; после ремонта машина участвует с момента ремонта.
- [x] **R3. Ремонт перед первым `calculate_rewards`** — ремонт сразу записывается с точным временем, но нерассчитанный доход пока нельзя забрать. Когда очередь доходит до ремонта, старый период закрывается, а новый начинается с времени ремонта.
- [x] **R4. Ремонт после `collect_fees`, но до `calculate_rewards`** — время сбора не определяет участие машины. Доход до ремонта относится к старому периоду, после точного времени ремонта — к новому.
- [x] **R5. Ремонт во время незавершённой очереди расчётов** — транзакция ремонта не пытается догнать очередь. Событие ожидает своей позиции, а после его обработки машина считается активной с точного времени ремонта.
- [x] **R6. Повторный ремонт** — разрешён даже при отставшей очереди. Каждое событие обрабатывается по времени, доход между ремонтами не прерывается, каждый ремонт оплачивает недостающую на тот момент прочность, а новая поломка считается через 5 дней после последнего ремонта.
- [x] **R7. Transfer и ремонт** — ремонтировать может только текущий owner Solana NFT asset; marketplace/delegate-полномочия этого права не дают. После transfer состояние machine PDA и накопленный доход следуют за asset.
- [x] **R8. Событие ремонта** — программа записывает точное время ремонта и новую поломку через 5 дней. Финансовые checkpoints заполняются позже, когда `calculate_rewards` доходит до события.
- [x] **R9. Формула стоимости ремонта** — полное восстановление стоит 25% от рассчитанного `$FARE`-дохода NFT после последнего mint/ремонта. Фактическая цена равна полной цене, умноженной на долю недостающих секунд от 5 дней; при базе `100 FARE` один недостающий день стоит `5 FARE`.
- [x] **R9a. Старый исторический алгоритм отменён** — цену не считаем через общий доход всех машин и поиск глобальной истории. Индивидуальная база NFT получается по checkpoint дохода одного веса и не сбрасывается обычным `claim`.
- [x] **R9b. Ранний ремонт** — если после прошлого ремонта машина заработала `20 FARE` и потеряла один день прочности, полная цена равна `20 × 25% = 5 FARE`, а фактический ремонт одного дня стоит `5 × 20% = 1 FARE`.
- [x] **R10. Ремонт и общий вес** — при обработке события ремонта вес добавляется в расчётный активный вес, но экономически участие начинается с точного времени ремонта, указанного в событии.
- [x] **R11. Недостаточная история ремонта** — если рассчитанная история короче срока восстанавливаемой прочности, учитывается только доступная часть без масштабирования. При отсутствии истории стоимость равна нулю.

### 4. Mint и transfer

- [x] **M1. Mint до `collect_fees`** — машина участвует в последующих рассчитанных отрезках начиная с точного времени mint.
- [x] **M2. Mint после `collect_fees`, но до начала серии** — машина может получить часть уже существующего нераспределённого пула, но только за отрезки после точного времени mint.
- [x] **M3. Mint после начала серии `calculate_rewards`** — событие относится к следующей серии; текущий зафиксированный расчёт не изменяется.
- [x] **M4. Transfer до claim накопленного дохода** — весь незабранный доход остаётся у NFT и становится доступен новому владельцу; transfer не создаёт расчётное событие.
- [x] **M5. Transfer после claim** — уже выплаченное не переходит, а оставшееся состояние NFT, прочность и будущий доход переходят новому владельцу без перезапуска периода.
- [x] **M6. Transfer сломанной машины** — новый owner получает NFT вместе с её `claimable` и решает, ремонтировать ли её; прежний owner после transfer не имеет доступа к `claim` и ремонту.
- [x] **M7. Отображение машины в Phantom** — кошелёк показывает Metaplex Core Asset с названием, изображением и metadata URI как коллекционный NFT. Прочность, доход и цена ремонта не дублируются в NFT-метаданные: frontend читает их из соответствующего Machine PDA.
- [x] **M8. Поддельный Core Asset** — Asset с похожими названием и изображением, но не принадлежащий официальной Core Collection, не признаётся машиной и не может использовать Machine PDA проекта.
- [x] **M9. Лимиты классов** — программа не позволяет выпустить больше 1000 NFT «Эконом», 300 «Комфорт», 100 «Бизнес» и 25 «Легенда». После достижения общего лимита 1425 дополнительный mint невозможен независимо от свободного лимита, переданного frontend.
- [x] **M10. Фиксация цены продажи** — до `start_sale` admin записывает четыре цены в lamports SOL, рассчитанные от ориентиров `$49 / $129 / $399 / $1099`. После старта изменить цены нельзя; каждый mint списывает точное зафиксированное количество SOL независимо от последующего курса.
- [x] **M11. Несколько NFT на одном кошельке** — один адрес может последовательно минтить любое количество машин. Каждый вызов создаёт одну NFT и проверяет только лимит выбранного класса и общий тираж; персонального лимита и счётчика покупок кошелька нет.
- [x] **M12. Публичный старт продажи** — после `start_sale` любой кошелёк может сразу выполнить mint. Программа не проверяет allowlist, ваучер раннего доступа или персональное разрешение.
- [x] **M13. Ручное открытие продажи** — до административного вызова `start_sale` mint отклоняется. После успешного вызова продажа открывается всем. Автоматического запуска по времени нет.
- [x] **M14. Готовые неизменяемые метаданные** — сразу после mint Phantom получает окончательные название, изображение, описание и признаки машины по её URI. Скрытого изображения и reveal нет. `ImmutableMetadata` официальной Core Collection не позволяет администратору позже заменить имя или URI машины.
- [x] **M15. Постоянные файлы NFT** — до `start_sale` команда проверяет, что каждая metadata JSON и связанное изображение доступны по Arweave URI, загруженному через Irys, а признаки соответствуют машине. `start_sale` отправляется только после этой внешней проверки; после блокировки URI проект не зависит от собственного web-сервера для отображения NFT.

### 5. Сложные комбинации

- **C1. Машина ломается, затем приходит комиссия, затем вызывается claim.**
- **C2. Машину чинят перед claim, пока в пуле уже есть деньги.**
- **C3. Новую NFT минтят перед первым claim большого пула.**
- **C4. Несколько машин ломаются, ремонтируются и передаются между claim.**
- **C5. `collect_fees` отправляет backend, а `claim` — обычный пользователь.**
- **C6. Backend не работает несколько дней, затем другой fee payer отправляет permissionless `collect_fees` и `calculate_rewards`.**

### 6. Пользовательские сценарии частично обработанного пула

- **U1. Пул 100 и четыре часовых отрезка** — после первого отрезка расчётный остаток равен 75, хотя физически в SPL vault всё ещё лежит 100.
- **U2. Два `calculate_rewards` подряд** — вторая транзакция продолжает с сохранённого события и не распределяет первые 25 повторно.
- **U3. `Claim` после одного обработанного отрезка** — пользователь получает только доход за обработанный отрезок; остальная сумма остаётся нераспределённой.
- **U4. Несколько владельцев забирают доход** — каждый получает только свою записанную долю, а физический баланс уменьшается только при фактической выплате.
- **U5. Новые комиссии после частичного расчёта** — новые деньги не смешиваются с уже начатым расчётным пулом.
- **U6. Машина ломается между двумя отрезками** — первый отрезок учитывается, следующие отрезки машина пропускает.
- **U7. Машина минтится или чинится между двумя отрезками** — она участвует только начиная с момента mint/ремонта.
- **U8. Одна машина имеет несколько периодов работы** — доход складывается из отдельных активных периодов до и после ремонта.
- **U9. Transfer машины с накопленным доходом** — накопленная сумма и незакрытый активный период переходят вместе с NFT.
- [x] **U10. Пул существует, но активных машин нет** — пустые отрезки не расходуют пул и не входят в распределяемое время. Деньги ждут первого активного периода и затем целиком делятся только между его машинами.

### 7. Функции протокола

- [ ] **F0. Creator Fee поступает прямо в PDA** — pump.fun направляет SOL на program-controlled PDA без промежуточного административного/backend-кошелька. До production сценарий обязательно проверяется на тестовом запуске; после поступления обработку может инициировать любой fee payer.
- [ ] **F0a. Тестовый pump.fun mint** — до создания основного `$FARE` проверяем фактический Token Program, supply, decimals, authorities, metadata, burn токенов из program vault и получение Creator Fee на PDA. Основной mint не создаётся, пока проверка не пройдена.
- [x] **F1. Успешный сбор Creator Fee** — `collect_fees` фиксирует новый SOL: 70% добавляются в `$FARE`-резерв, четыре доли по 5% — в отдельные stock-резервы, 10% переводятся команде. Swap и пользовательские начисления в этой транзакции не выполняются.
- [x] **F1a. Успешная покупка `$FARE`** — `process_fare_swap` меняет накопленный 70% SOL-резерв через Jupiter. Из фактически полученного `$FARE` 45/70 поступают в основной пул, 5/70 — в стажёрский, 20/70 сжигаются. Нераспределимый raw-остаток сохраняется в program vault и учитывается при следующей обработке.
- [x] **F2. Частичная ошибка stock-покупки** — если `process_stock_swap` для AMZNx не прошёл по slippage или ликвидности, транзакция AMZNx откатывается и её SOL остаётся в `stockReserve`. Успешные независимые покупки UBERx, TSLAx и GOOGLx не откатываются.
- [x] **F2a. Ошибка `$FARE` swap или burn** — вся `process_fare_swap` откатывается: основной и стажёрский пулы не пополняются, burn не учитывается, а исходный SOL остаётся в 70% резерве для повторной попытки.
- **F3. Новый `collect_fees` во время расчёта** — новые деньги относятся к следующему расчётному пулу и не меняют уже начатый расчёт.
- [x] **F4. `calculate_rewards` обрабатывает bounded batch** — caller задаёт `limit` не больше 20. После обработки курсор сохраняется, а следующая транзакция продолжает со следующего события. Попытка передать `limit > 20` отклоняется до изменения очереди.
- [x] **F5. Вызван `calculate_rewards` без новых денег** — очередь продвигается, события и активный вес обновляются, а обработанные отрезки получают нулевой доход. Будущие поступления по ним задним числом не распределяются.
- **F6. `Claim` во время незавершённого расчёта** — пользователь получает только уже рассчитанную сумму; необработанные отрезки ждут завершения расчёта.
- [x] **F7. Один пользователь владеет несколькими NFT** — каждый `claim(asset)` обрабатывает одну машину; `claim_all` и перебор NFT владельца отсутствуют.
- [x] **F8. Фактический состав выплаты** — если машине начислены `$FARE`, UBERx, TSLAx и GOOGLx, но AMZNx ещё не был куплен, `claim` переводит четыре фактически начисленных актива и ноль AMZNx. Программа не продаёт и не докупает активы ради фиксированного соотношения по стоимости и не создаёт AMZNx-долг.

### 8. Backend и permissionless-вызовы

- [x] **B0. Событие имеет только `confirmed`** — frontend может показать ожидание, но backend не записывает событие как окончательное и не запускает зависимую покупку или расчёт. Работа начинается после появления статуса `finalized`.
- [x] **B1. Backend отправляет `collect_fees` по порогу** — минимальная сумма задаётся off-chain. Программа разрешает более ранний permissionless-вызов, но слишком маленькие суммы оставляет в резервах без swap.
- [x] **B2. Backend регулярно отправляет `calculate_rewards`** — раз в минуту backend читает очередь и при необходимости продвигает её последовательными безопасными batch до актуального состояния.
- **B3. Backend остановился** — любой пользователь может вручную вызвать служебную функцию и продолжить работу.
- [x] **B4. Два разных вызывающих одновременно двигают очередь** — транзакции исполняются последовательно: первая обрабатывает свой batch, вторая читает уже обновлённый курсор и продолжает со следующих событий без двойного начисления.
- [x] **B5. Оплата служебной транзакции** — компенсации и бонуса нет; backend или другой fee payer полностью оплачивает network fee в SOL.
- [x] **B6. Backend перезапустился после простоя** — он читает текущие finalized PDA резервов, пулов и очередей и продолжает с их актуальных курсоров. Пропущенные транзакции не воспроизводятся по одной, а старое состояние MongoDB не используется для изменения on-chain сумм.
- [x] **B7. Backend повторил job после потери ответа RPC** — повторный swap со старым nonce отклоняется; повторный `collect_fees` не учитывает ранее распределённый вход; повторный `calculate_rewards` читает новый курсор и не начисляет уже обработанный отрезок второй раз. MongoDB-lock для денежной корректности не требуется.
- [x] **B8. MongoDB потеряна или повреждена** — campaign/backend данные и кэш восстанавливаются из автоматической ежедневной копии управляемой MongoDB. После восстановления backend заново читает finalized PDA Solana; значения резервов, очередей и начислений из backup не записываются обратно в контракт и не заменяют on-chain состояние.

### 8a. Стажёрская очередь

- [x] **T1. Много активаций за одну минуту** — все стажёры начинают со следующей полной минуты; стартовый вес объединяется в одной корзине, а окончания объединяются по своим минутам с учётом длительности ваучеров.
- [x] **T2. Граница минуты** — кошельки, активированные по разные стороны минутной границы, относятся к соседним корзинам и имеют разные `activeFrom`/`activeUntil`.
- [x] **T3. Повторное участие** — один кошелёк использует каждый `campaignId` один раз, но может одновременно активировать несколько машин разных кампаний.
- [x] **T4. Backend меняет длительность** — длительность находится в подписанном ваучере и влияет только на новую машину. Программа обновляет нужные minute-bucket PDA, не меняя уже активных стажёров.
- [x] **T5. Границы длительности** — ваучер от 1 часа до 7 дней принимается; иное значение отклоняется программой.
- [x] **T6. Несколько машин одного кошелька** — доход каждой кампании забирается отдельным `claim_trainee(campaignId)`; большое число найденных слов не создаёт цикл внутри одной транзакции.

### 8b. Административный Rescue

- [x] **A1. Rescue поддерживаемого актива** — admin может указать SOL, `$FARE` или любой поддерживаемый xStocks mint и вывести выбранную сумму из program-controlled vault. Наличие внутренних обязательств перед NFT технически не блокирует вывод, поэтому после Rescue vault может временно не покрывать пользовательские выплаты.
- [x] **A2. Rescue без паузы** — инструкция отклоняется без перевода активов. После отдельного успешного `pause` admin может выполнить Rescue; заблокированные проектные инструкции не могут одновременно изменить vault или обязательства.
- [x] **A3. Замена `$FARE` mint** — попытка изменить mint в рабочем режиме отклоняется. Во время глобальной паузы admin может записать новый адрес; старые raw-балансы и обязательства не превращаются в новый токен, а переносятся в отдельный legacy slot для последующих расчётов и выплат.
- [x] **A4. Незабранный `$FARE` при замене mint** — машина с начисленными `100` raw старого `$FARE` после `unpause` может забрать именно эти `100` старых токенов. Доход после migration boundary начисляется новым mint, а новый ремонт оплачивается из новой FARE-базы.
- [x] **A5. Повторная замена `$FARE`** — пока legacy vault содержит нераспределённый старый пул или непогашенные обязательства, установить ещё один mint нельзя. После выплаты старого пула и всех старых начислений legacy slot освобождается для возможной будущей миграции.

### 9. Solana stock-выплаты и аварийные случаи

- [x] **S0. Пользователь из запрещённой xStocks юрисдикции** — frontend и условия использования явно сообщают, что stock-функциями пользоваться нельзя. Технической блокировки по IP, кошельку или KYC нет; Solana-программа не определяет страну пользователя и остаётся permissionless.
- [ ] **S1. xStocks-инвентарь есть** — `claim` отправляет рассчитанную raw-долю только фактически купленных официальных xStocks mint на Solana. До реализации адрес каждого mint проверяется по официальным данным и ликвидности.
- [x] **S2. Stock-токен не удалось купить** — он не участвует в распределении и не создаёт долг перед NFT. Выделенный SOL остаётся в отдельном `stockReserve`; после успешной покупки stock-токен попадёт только в следующую серию.
- [x] **S2a. Деление stock-корзины** — xStocks-позиции `UBERx`, `TSLAx`, `GOOGLx` и `AMZNx` получают по 25% stock-бюджета, то есть по 5% Creator Fee. Если официальный mint или ликвидность позиции недоступны, её доля остаётся в отдельном SOL-резерве и не увеличивает остальные позиции.
- [x] **S2b. Защита цены stock-покупки** — backend подписывает ed25519-план по свежей котировке Jupiter с допуском 5%. Программа проверяет настроенный Jupiter program ID, входной SOL, выходной официальный xStocks mint, `minOut`, deadline и nonce. При худшем результате swap не выполняется, а выделенный SOL остаётся в резерве; собственный oracle не используется.
- [x] **S2d. Jupiter не нашёл маршрут** — stock-покупка не выполняется, начисление по этой позиции не создаётся, а её SOL остаётся в отдельном резерве. Остальные позиции могут быть обработаны независимо согласно решению SOL-9.
- [x] **S2e. Подмена Jupiter-маршрута** — транзакция отклоняется, если маршрут использует другой program ID, расходует больше разрешённого SOL, возвращает другой mint, даёт меньше `minOut` либо содержит просроченный или уже использованный nonce.
- [x] **S2c. Срок и повтор swap-плана** — подпись действует 10 минут. У каждого stock mint собственный nonce. Первый успешный план увеличивает nonce только этого mint; повтор и конкурент со старым nonce отклоняются.
- [x] **S3. Несколько NFT одного владельца** — доход и checkpoints хранятся в отдельном PDA каждой NFT; один `claim(asset)` не изменяет другие машины владельца.
- [x] **S4. Claim ровно в момент `activeUntil`** — машина уже сломана и не получает доход за время начиная с этой секунды.
- [x] **S5. Округление `$FARE`** — остаток минимальных единиц не теряется и добавляется в следующий `$FARE`-пул.
- [x] **S6. Округление stock-токенов** — raw-остаток каждого SPL mint учитывается отдельно и переносится в следующую серию этого же mint.
- [x] **S7. Неожиданная ошибка SPL-перевода при claim** — Solana-транзакция откатывается целиком; checkpoints и начисления NFT остаются доступными для повторной попытки.
- [x] **S8. Pause во время claim** — глобальная пауза блокирует `claim` и остальные проектные инструкции. Начисления и SPL-активы остаются в PDA-vaults и доступны после `unpause`.
- [x] **S9. Corporate action до `claim`** — NFT уже начислено 5 raw stock-токенов, но пользователь их не забрал. Multiplier меняется с 1.0 до 1.1: обязательство остаётся 5 raw, а frontend показывает 5.5 xStock. При `claim` пользователь получает ровно 5 raw, которые его кошелёк также показывает как 5.5.
- [x] **S9a. Corporate action после `claim`** — пользователь забрал 5 raw stock-токенов в свой кошелёк. Последующий dividend, split или reverse split меняет общий multiplier; raw-баланс остаётся 5, а отображаемое количество меняется автоматически.
- [x] **S9b. Старые обязательства и новая покупка** — во vault лежит 11 raw stock-токенов: 10 зарезервированы под уже рассчитанные claims, а 1 raw фактически получен новой покупкой. Старые получатели вместе забирают 10 raw; новая 1 raw единица входит в следующую расчётную серию.
- [x] **S9c. Изменился Token-2022 `ScaledUiAmount`** — raw-баланс vault, raw-обязательства NFT и raw-сумма перевода не пересчитываются. Frontend до и после `claim` отображает их с текущим multiplier.
- [x] **S9c1. Транзакция на границе multiplier** — специального окна остановки нет. Если Jupiter quote сформирован перед активацией multiplier, а `process_stock_swap` исполняется после неё и всё ещё проходит установленный `minOut`, результат принимается. Возможное небольшое ценовое расхождение не компенсируется и не пересчитывается.
- [ ] **S9d. Эмитент заменил stock mint** — автоматическую конвертацию старого mint в новый не предполагаем. До поддержки такого corporate action отдельно определяются источник официального нового адреса, коэффициент обмена и судьба старых обязательств.
- [x] **S10. Машина во время глобальной паузы** — если до паузы у машины оставалось 10 часов прочности, после паузы любой длительности у неё остаются те же 10 часов. За остановленное время доход не начисляется. После `unpause` единое внутреннее время продолжает идти без массового переноса сроков всех машин.
- [x] **S10a. Transfer машины во время паузы** — владелец может передать или продать Metaplex Core Asset стандартной Core-инструкцией. Machine PDA не меняет прочность и расчётные значения; после `unpause` только новый owner может вызвать `claim` или ремонт и получить весь оставшийся у NFT доход.
- [x] **S10b. Попытка использовать машину после transfer во время паузы** — проектные `claim`, ремонт и другие действия всё равно отклоняются до `unpause`, независимо от смены владельца. Transfer не позволяет обойти паузу.

### 10. Подключение кошелька

- [x] **W1. Обычный Phantom** — пользователь подключает существующий Solana-аккаунт через Wallet Standard, а frontend получает только публичный адрес и запрашивает подписи конкретных транзакций.
- [x] **W2. Phantom создан через Google/Apple** — для программы это такой же Solana public key. Проект не получает данные социальной учётной записи и не различает способ восстановления кошелька.
- [x] **W3. Пользователь потерял доступ** — проект не хранит seed-фразу или ключ и не может восстановить кошелёк либо перенести NFT. Восстановление выполняется средствами Phantom.
- [x] **W4. У пользователя нет SOL** — mint, `claim`, ремонт, активация стажёра и `claim_trainee` не отправляются, пока пользователь самостоятельно не пополнит кошелёк. Backend не выдаёт SOL и не подменяет fee payer.
- [x] **W5. Backend вызывает служебную инструкцию** — backend оплачивает SOL network fee только за отправленные им `collect_fees`, `process_fare_swap`, `process_stock_swap` или `calculate_rewards`. Если ту же permissionless-инструкцию вызывает другой кошелёк, он платит самостоятельно и не получает компенсацию.
- [x] **W6. Mint создаёт новые accounts** — покупатель оплачивает network fee и rent-exempt deposit Core Asset, Machine PDA и новой страницы event queue, если именно его mint требует расширения. Казна не возмещает эти расходы.
- [x] **W7. Первый stock-claim без token account** — если NFT действительно начислен конкретный xStocks mint, `claim` может создать недостающий associated token account за SOL пользователя. Accounts для stock mint с нулевой выплатой не создаются.
- [x] **W8. Активация стажёра создаёт PDA** — пользователь оплачивает Trainee PDA и нужные minute-bucket accounts, создаваемые его транзакцией. Это не меняет отдельный 5% пул и не даёт пользователю дополнительной награды.
