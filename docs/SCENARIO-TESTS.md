# Сценарии проверки экономики

Этот документ нужен для проверки распределений, прочности, mint и transfer до реализации контрактов.

## Правило связанных сценариев

Сценарии используют одну общую текущую модель проекта. Если решение в одном сценарии меняется, все остальные сценарии нужно повторно проверить и пересчитать под новое решение. Нельзя считать старые выводы действующими, если они опираются на изменённое правило.

## Базовые условия

- Максимальная прочность машины: `X = 5 дней`.
- `syncFees()` только забирает комиссии на наши контракты и покупает/пополняет stock-инвентарь.
- Распределение дохода происходит в `claim()`.
- Накопленный доход принадлежит NFT и переходит её новому владельцу.
- Свежесминченная NFT не получает комиссии, накопленные до её минта.
- Для примеров используются четыре машины:

| Машина | Вес |
|---|---:|
| A | 1 |
| B | 3 |
| C | 10 |
| D | 30 |

## Группы сценариев

### Зафиксированное правило распределения

Пул распределяется пропорционально времени и весу активных машин. Для каждого временного отрезка определяется его доля от общего периода, затем эта сумма делится между активными машинами по весам. Это сознательно сглаживает резкие изменения и повышает шанс раннего дохода для новых пользователей. Правило будет открыто описано в продуктовой документации.

### Правило остатка пула

Если в пуле физически лежит `100`, а расчёт обработал один из четырёх равных часовых отрезков, этому отрезку назначается `25`, а для следующих отрезков остаётся `75`. Физический баланс контракта всё ещё равен `100`, но `25` уже зарезервированы за машинами первого отрезка и повторно не участвуют в расчёте.

### 1. Распределение

- [x] **D1. Первый claim после syncFees** — первый claim фиксирует общий пул и долю каждой активной NFT, но выплачивает только вызывающему владельцу.
- [x] **D2. Второй claim** — второй владелец получает только свою заранее рассчитанную долю; доход остальных машин не меняется.
- [x] **D3. Повторный claim одной машины** — повторный claim без новых комиссий выплачивает 0; новые комиссии создают новую выплату.
- [x] **D4. Несколько `CollectFees()` до `CalculateRewards()`** — все собранные деньги объединяются. В момент расчёта весь текущий пул распределяется по временным отрезкам активности; время отдельных сборов не учитывается.
- [x] **D5. Новые комиссии после `CalculateRewards()`** — старый пул больше не пересчитывается; новые деньги распределяются отдельным расчётом по текущим активным машинам.
- [x] **D6. Нет активных машин** — при нулевом общем весе деньги остаются в пуле и не теряются.
- [x] **D7. Округление** — минимальный нераспределимый остаток каждого ERC-20 остаётся на контракте и переходит в следующую серию того же токена.

### 2. Потеря прочности

- [x] **P1. Claim через 2 дня после минта** — `Claim()` выплачивает рассчитанный доход, но не меняет `activeUntil`; до поломки остаётся 3 дня.
- [x] **P2. Claim после полного истечения 5 дней** — машина получает только рассчитанный доход до `activeUntil`; время после поломки не оплачивается.
- [x] **P3. Claim ровно в момент истечения** — при `block.timestamp == activeUntil` машина уже сломана; доход начисляется только за полуоткрытый период `[activeFrom, activeUntil)`.
- [x] **P4. Машина ломается между двумя claim** — событие `EXPIRE` исключает её из активного веса при обработке очередью; следующий `Claim()` использует сохранённую конечную границу периода и не начисляет доход после `activeUntil`.
- [x] **P5. Одновременно ломаются несколько машин** — каждая поломка является отдельным событием и отдельным шагом batch-лимита, даже при одинаковой секунде. Между событиями с одинаковым временем доход равен нулю, но каждая NFT отдельно исключается из активного веса. При равном времени используется порядок добавления, а batch-курсор хранит `timestamp + eventNumber`.
- [x] **P6. Большая очередь сломанных машин** — события хранятся в min-heap по `timestamp + eventNumber`. `CalculateRewards()` извлекает максимум 20 ближайших записей и продолжает следующей транзакцией; неактуальные события также извлекаются отдельными ограниченными шагами.

### 3. Ремонт

- [x] **R1. Ремонт до поломки** — если осталось 2 часа из 5 дней, стоимость ремонта считается за недостающие 4 дня 22 часа. Старая запись о поломке через 2 часа удаляется/делается неактуальной, а в очередь добавляется новая запись о поломке через 5 дней после ремонта.
- [x] **R2. Ремонт после поломки** — перед запуском нового периода контракт автоматически закрывает старый период и добавляет его доход в `claimable`; после ремонта машина участвует с момента ремонта.
- [x] **R3. Ремонт перед первым `CalculateRewards()`** — ремонт сразу записывается с точным временем, но нерассчитанный доход пока нельзя забрать. Когда очередь доходит до ремонта, старый период закрывается, а новый начинается с времени ремонта.
- [x] **R4. Ремонт после `CollectFees()`, но до `CalculateRewards()`** — время `CollectFees()` не определяет участие машины. Доход до ремонта относится к старому периоду машины, после точного времени ремонта — к новому.
- [x] **R5. Ремонт во время незавершённой очереди расчётов** — транзакция ремонта не пытается догнать очередь. Событие ожидает своей позиции, а после его обработки машина считается активной с точного времени ремонта.
- [x] **R6. Повторный ремонт** — разрешён даже при отставшей очереди. Каждое событие обрабатывается по времени, доход между ремонтами не прерывается, каждый ремонт оплачивает недостающую на тот момент прочность, а новая поломка считается через 5 дней после последнего ремонта.
- [x] **R7. Transfer и ремонт** — ремонтировать может только текущий владелец NFT; ERC-721 approvals этого права не дают. После продажи прочность, события и накопленный доход остаются у NFT и принадлежат новому владельцу.
- [x] **R8. Событие ремонта** — контракт записывает точное время ремонта и новую поломку через 5 дней. Финансовые контрольные значения заполняются позже, когда `CalculateRewards()` доходит до события.
- [x] **R9. Формула стоимости ремонта** — полное восстановление стоит 25% от выбранной базы `$FARE`-дохода самой NFT. Фактическая цена равна полной цене, умноженной на долю недостающих секунд от 5 дней; при базе `100 FARE` один недостающий день стоит `5 FARE`.
- [x] **R9a. Старый исторический алгоритм отменён** — цену больше не считаем через общий доход всех машин, `totalActiveWeight`, линейный или бинарный поиск глобальной истории. Способ получения индивидуальной `fareBase` уточняется отдельно.
- [x] **R10. Ремонт и общий вес** — при обработке события ремонта вес добавляется в расчётный активный вес, но экономически участие начинается с точного времени ремонта, указанного в событии.
- [x] **R11. Недостаточная история ремонта** — если рассчитанная история короче срока восстанавливаемой прочности, учитывается только доступная часть без масштабирования. При отсутствии истории стоимость равна нулю.

### 4. Mint и transfer

- [x] **M1. Mint до `CollectFees()`** — машина участвует в последующих рассчитанных отрезках начиная с точного времени минта.
- [x] **M2. Mint после `CollectFees()`, но до начала серии** — машина может получить часть уже существующего нераспределённого пула, но только за отрезки после точного времени минта.
- [x] **M3. Mint после начала серии `CalculateRewards()`** — событие относится к следующей серии; текущий зафиксированный расчёт не изменяется.
- [x] **M4. Transfer до claim накопленного дохода** — весь незабранный доход остаётся у NFT и становится доступен новому владельцу; transfer не создаёт расчётное событие.
- [x] **M5. Transfer после claim** — уже выплаченное не переходит, а оставшееся состояние NFT, прочность и будущий доход переходят новому владельцу без перезапуска периода.
- [x] **M6. Transfer сломанной машины** — новый владелец получает NFT вместе с её старым `claimable` и сам решает, ремонтировать ли её; старый владелец после transfer не имеет доступа к `Claim()` и ремонту.

### 5. Сложные комбинации

- **C1. Машина ломается, затем приходит комиссия, затем вызывается claim.**
- **C2. Машину чинят перед claim, пока в пуле уже есть деньги.**
- **C3. Новую NFT минтят перед первым claim большого пула.**
- **C4. Несколько машин ломаются, ремонтируются и передаются между claim.**
- **C5. syncFees вызывается backend, а claim — обычным пользователем.**
- **C6. Backend не работает несколько дней, затем кто-то вызывает syncFees вручную.**

### 6. Пользовательские сценарии частично обработанного пула

- **U1. Пул 100 и четыре часовых отрезка** — после первого отрезка расчётный остаток равен 75, хотя физически на контракте всё ещё лежит 100.
- **U2. Два `CalculateRewards()` подряд** — второй вызов продолжает с сохранённого события и не распределяет первые 25 повторно.
- **U3. `Claim` после одного обработанного отрезка** — пользователь получает только доход за обработанный отрезок; остальная сумма остаётся нераспределённой.
- **U4. Несколько владельцев забирают доход** — каждый получает только свою записанную долю, а физический баланс уменьшается только при фактической выплате.
- **U5. Новые комиссии после частичного расчёта** — новые деньги не смешиваются с уже начатым расчётным пулом.
- **U6. Машина ломается между двумя отрезками** — первый отрезок учитывается, следующие отрезки машина пропускает.
- **U7. Машина минтится или чинится между двумя отрезками** — она участвует только начиная с момента mint/ремонта.
- **U8. Одна машина имеет несколько периодов работы** — доход складывается из отдельных активных периодов до и после ремонта.
- **U9. Transfer машины с накопленным доходом** — накопленная сумма и незакрытый активный период переходят вместе с NFT.
- **U10. Пул существует, но активных машин нет** — расчёт не расходует пул; деньги ждут появления активной машины.

### 7. Функции протокола

- **F1. Успешный `CollectFees()`** — комиссии переходят на наши контракты, stock-инвентарь пополняется, пользовательские начисления ещё не выплачиваются.
- [x] **F2. Частичная ошибка `CollectFees()`** — успешные направления сохраняются. Доля stock-токена, покупка которого не прошла по slippage или ликвидности, остаётся в его `stockReserve` и повторяется позже; остальные пулы и покупки не откатываются.
- **F3. Новый `CollectFees()` во время расчёта** — новые деньги относятся к следующему расчётному пулу и не меняют уже начатый расчёт.
- **F4. `CalculateRewards()` обрабатывает ровно 20 событий** — курсор очереди сохраняется, следующий вызов продолжает со следующего события.
- [x] **F5. Вызван `CalculateRewards()` без новых денег** — очередь продвигается, события и активный вес обновляются, а обработанные отрезки получают нулевой доход. Будущие поступления по ним задним числом не распределяются.
- **F6. `Claim` во время незавершённого расчёта** — пользователь получает только уже рассчитанную сумму; необработанные отрезки ждут завершения расчёта.
- [x] **F7. Один пользователь владеет несколькими NFT** — каждый `Claim(tokenId)` обрабатывает одну выбранную машину; `ClaimAll()` и перебор всех NFT владельца в первой версии отсутствуют.

### 8. Backend и permissionless-вызовы

- [x] **B1. Backend вызывает `CollectFees()` по порогу** — минимальная сумма задаётся off-chain настройкой backend. Контракт разрешает более ранний permissionless-вызов, но слишком маленькие суммы оставляет в соответствующих резервах без swap.
- [x] **B2. Backend регулярно вызывает `CalculateRewards()`** — раз в минуту backend проверяет наличие готовых событий и при необходимости последовательно продвигает очередь транзакциями максимум по 20 событий до актуального состояния.
- **B3. Backend остановился** — любой пользователь может вручную вызвать служебную функцию и продолжить работу.
- [x] **B4. Два разных вызывающих одновременно двигают очередь** — транзакции исполняются последовательно: первая обрабатывает свой batch, вторая читает уже обновлённый курсор и продолжает со следующих событий без двойного начисления.
- [x] **B5. Оплата служебного вызова** — компенсации и бонуса нет при любом результате; backend или пользователь полностью оплачивает газ самостоятельно.

### 9. Stock-выплаты и аварийные случаи

- [x] **S1. Stock-инвентарь есть** — `Claim` отправляет пользователю рассчитанную долю только тех stock-токенов, которые были фактически куплены и включены в расчётную серию.
- [x] **S2. Stock-токен не удалось купить** — он не участвует в распределении и не создаёт долг перед NFT. Денежная доля остаётся в `stockReserve`; после успешной покупки токен попадёт только в следующую серию.
- [x] **S2a. Деление stock-корзины** — `UBER`, `LYFT`, `TSLA` и `GRAB` получают равные доли по 25% stock-бюджета; резерв неудавшейся покупки не увеличивает доли остальных токенов.
- [x] **S2b. Защита цены stock-покупки** — backend подписывает короткоживущий план по свежей котировке с начальным допуском 5%. При худшем результате swap не выполняется, а сумма остаётся в резерве; on-chain oracle не используется.
- [x] **S3. Несколько NFT одного владельца** — доход и контрольные значения хранятся отдельно у каждой NFT; один `Claim(tokenId)` не изменяет начисления других машин владельца.
- [x] **S4. Claim ровно в момент `activeUntil`** — машина уже сломана и не получает доход за время начиная с этой секунды.
- [x] **S5. Округление `$FARE`** — остаток минимальных единиц не теряется и добавляется в следующий `$FARE`-пул.
- [x] **S6. Округление stock-токенов** — остаток каждого stock-токена учитывается отдельно и переносится в следующую серию этого же токена.
- [x] **S7. Неожиданная ошибка токена при Claim** — вся транзакция откатывается без частичной выплаты; начисления NFT остаются доступными для повторного `Claim()` после устранения ошибки.
- [x] **S8. Pause во время Claim** — глобальная пауза блокирует `Claim()` и остальные изменяющие операции. Начисления и активы остаются на контракте и становятся доступны после `unpause`.

## Формат разбора

Для каждого сценария фиксируем:

```text
Начальное состояние:
Действия по порядку:
Кто имеет право на доход:
Сколько получает каждая машина:
Сколько прочности остаётся:
Что записывает контракт:
Решение:
```
