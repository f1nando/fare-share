# Оставшиеся вопросы перед запуском

Здесь собраны только решения, которые ещё не приняты для Solana-версии FARE Taxi Park. Старый EVM-вариант в этот список не входит.

Можно ответить одним сообщением, например:

```text
1-1, 2-1, 3-2, 4-1...
Дополнение к 12: https://x.com/...
```

Если подходят все рекомендуемые варианты, достаточно написать: `Везде 1` и отдельно передать только публичные данные, которых пока нет. Приватные ключи, seed-фразы, RPC-токены и API-ключи в чат присылать нельзя.

## NFT и metadata

### 1. Язык и содержание описаний NFT

Описание — это постоянный текст, который Phantom и маркетплейсы читают из metadata JSON. Прочность, накопленный доход и цена ремонта туда не записываются: они меняются и читаются из контракта.

1. **Короткое описание на английском — рекомендуется.** Например: `An Economy taxi from FARE Taxi Park. Rewards depend on actual protocol fees. No fixed APY.` Для других классов меняется название класса.
2. Такое же короткое описание на русском.
3. Только нейтральная фраза `An Economy taxi from FARE Taxi Park`, без упоминания выплат.

### 2. Какие постоянные attributes записать

Attributes помогают кошелькам и маркетплейсам показывать различия между классами.

1. **`Class`, `Weight`, `Max Supply` — рекомендуется.** Только неизменяемые признаки.
2. Только `Class` и `Weight`.
3. Вообще без attributes.

### 3. Изображение и metadata коллекции

Кроме четырёх машин, самой коллекции `FARE Taxi Park` нужны общий JSON и изображение.

1. **Сделать простую общую обложку из четырёх готовых машин — рекомендуется.** Сначала показать на согласование.
2. Использовать жёлтую машину «Эконом» как изображение всей коллекции.
3. Заказчик позже передаст отдельный логотип или обложку.

### 4. Загрузка в Arweave через Irys

Это создаст постоянные ссылки для четырёх изображений, четырёх JSON и коллекции. После включения `ImmutableMetadata` исправить ссылку будет нельзя.

1. **Я подготавливаю файлы и скрипт; загрузку запускаем отдельно после финальной проверки и пополнения кошелька — рекомендуется.**
2. Заказчик самостоятельно загружает файлы и передаёт готовые URI.
3. Сначала используем временные URI только в devnet, окончательную загрузку откладываем до mainnet.

## Токен и тестовый запуск

### 5. Проверка pump.fun до основного `$FARE`

Нужно подтвердить реальный путь Creator Fee, Token Program, burn и работу после graduation. Локальный тест не способен доказать поведение внешней площадки.

1. **Сначала отдельный дешёвый тестовый токен и полный devnet/доступный тестовый прогон, затем основной `$FARE` — рекомендуется.**
2. Создать тестовый токен, но проверить только получение Creator Fee и burn.
3. Сразу запускать основной `$FARE` без отдельного тестового токена — самый рискованный вариант.

### 6. Когда создавать основной `$FARE`

При создании токена нужно уже знать адрес программы и её `pumpCreator` PDA.

1. **После успешного тестового запуска, готовых metadata и зафиксированного Program ID — рекомендуется.**
2. Сразу после фиксации Program ID, не дожидаясь готовых NFT metadata.
3. Заказчик создаёт токен самостоятельно и позже передаёт публичный mint-адрес.

## Production-кошельки и инфраструктура

### 7. Куда отправлять 10% комиссии и оплату mint

Это публичный `TEAM_ACCOUNT`; приватный ключ контракту не нужен.

1. **Отдельный Phantom-кошелёк проекта — рекомендуется.** Не использовать личный повседневный кошелёк.
2. Личный Phantom-кошелёк владельца проекта.
3. Указать адрес позже; до этого production initialize не выполнять.

### 8. Как подготовить служебные ключи

Нужны три разные пары: admin, backend signer и worker. Multisig по принятому решению не используется.

1. **Сгенерировать их локально непосредственно перед запуском, сохранить в production `.env`, а admin дополнительно скопировать в отдельный backup — рекомендуется.**
2. Заказчик передаёт уже созданные keypair-файлы безопасным способом вне чата.
3. Временно использовать одни devnet-ключи, а перед mainnet создать новые.

### 9. RPC и DAS для Solana

RPC отправляет транзакции и читает accounts; DAS находит NFT пользователя для гаража.

1. **Один управляемый провайдер с RPC и DAS в одном аккаунте — рекомендуется.** Меньше настроек и точек отказа.
2. Разные провайдеры для RPC и DAS.
3. Публичный RPC и отдельный DAS — дешевле, но ограничения и нестабильность выше.

### 10. Production MongoDB

MongoDB хранит индекс событий, кампании и служебные jobs, но не заменяет on-chain источник истины.

1. **Управляемая MongoDB с автоматическими backup — рекомендуется.**
2. MongoDB на том же сервере, что backend, с собственным ежедневным backup.
3. Сначала локальная MongoDB для закрытого теста; production выбрать позже.

### 11. Размещение frontend и backend

1. **Статический frontend отдельно, backend/worker на одном небольшом сервере, MongoDB управляемая — рекомендуется.**
2. Frontend, backend, worker и MongoDB на одном сервере — проще, но единая точка отказа.
3. Пока запускать всё только на этом компьютере для закрытого теста.

### 12. Production-домен

Он нужен для frontend URL, CORS и публичных ссылок.

1. **Использовать отдельный домен проекта; точное имя передать перед публикацией — рекомендуется.**
2. Использовать поддомен уже существующего сайта заказчика.
3. Пока оставить технический адрес хостинга для закрытого теста.

## Публичные материалы

### 13. Ссылка на X/Twitter с кодовыми словами

1. **Использовать официальный аккаунт проекта и показать прямую ссылку во frontend — рекомендуется.** Нужно передать публичный URL.
2. Использовать личный аккаунт владельца проекта.
3. Пока не показывать ссылку; кампании стажёров запускать только после её добавления.

### 14. Юридическое предупреждение

Геоблокировку по принятому решению не делаем.

1. **Оставить короткое общее предупреждение и добавить ссылку на отдельные Terms — рекомендуется.** Текст Terms должен быть проверен юристом перед публичным запуском.
2. Оставить только текущий короткий текст без отдельной страницы Terms.
3. Заказчик передаёт полностью готовый юридический текст.

### 15. Финальные пользовательские тексты

1. **Оставить текущий минимальный русский интерфейс, заменив только реальные ссылки и значения — рекомендуется.**
2. Сделать интерфейс полностью английским.
3. Добавить переключатель русского и английского — больше работы и ещё один слой текстов.

## Цена, проверка и выпуск

### 16. Фиксация mint-цен в SOL

Ориентиры уже выбраны: `$49 / $129 / $399 / $1099`. Контракт хранит точные lamports и не использует oracle.

1. **Перед `start_sale` скрипт показывает пересчёт по текущему курсу, владелец один раз подтверждает четыре значения — рекомендуется.**
2. Заказчик вручную передаёт четыре окончательные цены в SOL.
3. Округлить цены до простых значений SOL заранее и больше не привязывать их точно к долларам.

### 17. Независимая проверка контракта

Контракт управляет реальными токенами; локальные тесты снижают риск, но не заменяют взгляд другого специалиста.

1. **Заказать хотя бы одну независимую focused-проверку денежного контура до mainnet-продажи — рекомендуется.**
2. Запустить закрытый devnet-тест с несколькими людьми, но без платного аудита.
3. Ограничиться нашими тестами и сразу перейти к mainnet — самый рискованный вариант.

### 18. Когда окончательно отключить обновление программы

Отзыв upgrade authority необратим: после него ошибку в этом deployment исправить нельзя, можно только публиковать новую программу.

1. **После тестового pump.fun прогона, независимой проверки и успешного mainnet smoke, но до открытия публичной продажи — рекомендуется.**
2. Через 7 дней после открытия продажи, чтобы сохранить возможность быстро исправить первый инцидент.
3. Не отзывать upgrade authority и оставить программу обновляемой.

## Что не является вопросом

После ответов всё равно потребуются фактические публичные адреса и отдельные действия: Program ID, `$FARE` mint, `TEAM_ACCOUNT`, RPC/DAS URL, домен, Twitter URL, цены в lamports, Arweave URI и явная команда на deploy. Четыре xStocks mint перед mainnet будут повторно проверены автоматически. Push, загрузка в Arweave, создание токена и deploy без отдельной команды не выполняются.
