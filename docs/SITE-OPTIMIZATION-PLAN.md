# План оптимизации производительности сайта

Статус: запланировано. Этапы выполняются последовательно, каждый отдельным логическим изменением с focused-проверкой и локальным commit.

Этот документ касается производительности всего сайта Fare Share: WebGL-фона, анимированной стены машин, изображений, видео, начальной загрузки и устойчивости публичного backend при наплыве пользователей. Завершённая история оптимизации симуляции города находится в [OPTIMIZATION-PLAN.md](OPTIMIZATION-PLAN.md), результаты — в [OPTIMIZATION-RESULTS.md](OPTIMIZATION-RESULTS.md).

## Цель

- Сохранить текущий внешний вид и поведение сайта.
- Не допускать устойчивых рывков на согласованных мобильных и настольных устройствах.
- Снижать качество только там, где измерения показывают, что устройство не укладывается в бюджет кадра.
- Не усложнять архитектуру и не добавлять зависимости без измеримой пользы.

Абсолютно гарантировать одинаковую плавность на любом устройстве невозможно. Готовность подтверждается на выбранных реальных устройствах и одинаковых production-сборках.

## Целевые бюджеты

- Desktop: p95 интервала кадра не выше 20 мс.
- Средний современный телефон: p95 не выше 30 мс.
- Во время обычного движения нет повторяющихся кадров длиннее 100 мс.
- После прогрева нет устойчивого роста количества DOM-узлов, WebGL-ресурсов и используемой памяти.
- Первый экран остаётся интерактивным во время загрузки фоновых материалов.

Цели уточняются после базового замера. Средний FPS не должен скрывать редкие длинные кадры.

## Текущая база

- Симуляция трафика уже вынесена в Worker, невидимые машины отсекаются, скрытая вкладка останавливает WebGL-loop, DPR ограничен значением 1.6.
- WebGL использует antialiasing, мягкие динамические тени и shadow map 2048 × 2048.
- Стена машин создаёт до 84 карточек. В каждой карточке используется 15 отдельных изображений дорожной разметки — около 1260 элементов `img` только для разметки.
- Обработчик движения указателя измеряет положение всех карточек через `getBoundingClientRect()`.
- PNG коллекции NFT занимают суммарно около 11.5 МБ.
- Три ролика How It Works занимают около 1.9 МБ и имеют `src`, хотя сейчас скрыты.
- У изображений нет общей стратегии `loading="lazy"`, `decoding="async"`, responsive thumbnails и современных форматов.
- Текущая production-сборка: Three.js — 522 КБ minified / 133 КБ gzip; React client — 223 / 69 КБ; код города — 112 / 44 КБ.

## Общий цикл этапа

1. Зафиксировать production-замер «до» на том же устройстве и сценарии.
2. Выполнить только один этап или явно выделенный подэтап.
3. Запустить минимальные связанные тесты, build и один целевой browser smoke, если менялся пользовательский сценарий.
4. Повторить тот же замер и проверить внешний вид.
5. Оставить изменение только при подтверждённой пользе без заметной визуальной регрессии.
6. Записать результат в [OPTIMIZATION-RESULTS.md](OPTIMIZATION-RESULTS.md) или отдельный краткий раздел результатов сайта и создать локальный commit.

## Очередь этапов

### S-01. Зафиксировать базовый замер всего сайта

**Работа:** добавить или использовать короткий production-сценарий, который отдельно измеряет первый экран, прокрутку, секцию стены машин и возвращение к WebGL-фону. Записывать p95/p99 кадра, long tasks, количество DOM-узлов, загруженные байты и WebGL-метрики.

**Готовность:** есть воспроизводимый отчёт desktop и хотя бы одного реального телефона. Известно, какие секции ограничены CPU, GPU, layout или сетью.

### S-02. Останавливать невидимую работу

**Работа:** приостанавливать WebGL rendering loop, когда фон полностью закрыт непрозрачной секцией или не виден. Останавливать CSS-анимации стены машин вне viewport. Возобновление не должно создавать скачок времени, камеры или трафика.

**Проверки:** переходы между секциями, скрытие/возврат вкладки, reduced motion, один browser smoke.

**Готовность:** под непрозрачной секцией WebGL не создаёт кадры; вне экрана стена машин не анимируется; возврат визуально плавный.

### S-03. Облегчить стену машин

**Статус:** реализовано, визуальная проверка на целевых телефонах ожидается. Пятнадцать `img` разметки в карточке заменены одним SVG-pattern с одним исходным изображением. React создаёт только 2–7 видимых колонок по текущему breakpoint. Стена, колонки и дороги приостанавливаются вне viewport. Координаты карточек кэшируются и при движении указателя обновляются не чаще одного раза в 500 мс; постоянный `will-change` у каждой дороги удалён. Редактор машин и сайт используют один компонент разметки и одинаково применяют сохранённые расстояние, траекторию, положение, размер, угол, прозрачность и скорость.

**Работа:** заменить 15 `img` дорожной разметки в каждой карточке одним повторяемым background, SVG или эквивалентным лёгким слоем. Рендерить только нужное для текущей ширины число колонок. Убрать лишние постоянные compositor layers. Не измерять все карточки при каждом pointer move: кэшировать границы и обновлять их после resize/scroll либо обрабатывать только ближайшую область.

**Проверки:** бесшовность циклов, hover/click фар, desktop и mobile layout, reduced motion, browser performance smoke.

**Готовность:** DOM и число одновременно анимируемых слоёв заметно уменьшены; композиция и скорость движения визуально сохранены; layout-work при движении указателя не создаёт длинных кадров.

### S-04. Добавить адаптивное качество WebGL

**Статус:** реализовано, проверка на слабом реальном телефоне ожидается. Обычная сцена стартует с High, измеряет p95 интервала кадров первые 2.5 секунды и затем продолжает контроль окнами по 4 секунды. При нехватке запаса профиль понижается сразу, повышение после первого окна требует двух успешных окон подряд. Разные пороги повышения и понижения предотвращают постоянное переключение. Профили меняют только DPR и тени; плотность, состояние Worker и существующие машины не меняются. Benchmark-режим остаётся фиксированным.

**Работа:** в первые секунды измерять реальный кадр и выбирать минимально необходимое качество с гистерезисом, чтобы режим не переключался постоянно. Начальные профили для проверки:

| Профиль | DPR | Shadow map | Плотность/эффекты |
|---|---:|---:|---|
| Max | до 1.6 | 2048 | настройка пользователя |
| High | до 1.4 | 1024 | настройка пользователя |
| Medium | до 1.2 | 512 | настройка пользователя |
| Low | 1.0 | выключены | настройка пользователя |

Сначала сравнить отдельные параметры. Не снижать плотность машин, если достаточно DPR или теней. Выбор делать по измеренному времени кадров, а не user-agent.

**Проверки:** отсутствие частых переключений, восстановление после фоновой вкладки, desktop/mobile screenshot, benchmark основного и stress-сценария.

**Готовность:** слабое устройство автоматически входит в бюджет; сильное сохраняет текущее качество; переключение не вызывает заметного зависания.

### S-05. Оптимизировать изображения

**Работа:** конвертировать тяжёлые PNG в WebP/AVIF с сохранением прозрачности и визуального качества. Добавить размеры, responsive-варианты, `loading="lazy"` и `decoding="async"` для изображений ниже первого экрана. Для сцен из API отдавать thumbnails подходящего размера, не загружать полноразмерный оригинал в маленькую карточку.

**Проверки:** сравнение прозрачности и качества, отсутствие layout shift, network trace desktop/mobile, fallback при недоступном API.

**Готовность:** существенно снижены загруженные и декодированные байты; первый экран не ждёт изображения нижних секций; внешний вид сохранён.

### S-06. Загружать видео только перед показом

**Работа:** скрытым роликам не задавать `src`. Если секция снова использует видео, подключать источник через IntersectionObserver незадолго до появления, ставить подходящий poster и останавливать видео вне viewport.

**Проверки:** network trace при открытии страницы и при прокрутке к секции, autoplay на поддерживаемых мобильных браузерах, fallback poster.

**Готовность:** при обычном открытии скрытые ролики не загружаются; при показе секции нет заметной пустой вспышки.

### S-07. Облегчить начальную загрузку JavaScript

**Работа:** динамически загружать код WebGL и некритические секции после появления основного интерфейса, не меняя визуальную последовательность первого экрана. Проверить, действительно ли разделение уменьшает main-thread blocking; не дробить код на множество мелких запросов без пользы.

**Проверки:** production build, cold-load trace, медленная сеть/CPU, отсутствие двойной инициализации в React StrictMode во время разработки.

**Готовность:** сокращено время до первого интерактивного экрана и начальная работа main thread; фон появляется без заметного скачка layout.

### S-08. Пропускать layout/paint нижних секций

**Работа:** проверить `content-visibility: auto` и `contain-intrinsic-size` для тяжёлых секций ниже первого экрана. Применять только там, где это не ломает якоря, IntersectionObserver, sticky/fixed элементы и точность макета.

**Проверки:** прямые переходы по якорям, прокрутка в обе стороны, desktop/mobile layout, browser smoke.

**Готовность:** начальный layout/paint дешевле, секции появляются без скачка высоты.

### S-09. Итоговый performance gate

**Работа:** повторить полный базовый сценарий на тех же устройствах. Зафиксировать итоговые p95/p99, long tasks, загрузку, DOM, память и выбранный профиль WebGL. Добавить короткую регрессионную проверку критичного сценария; не запускать полный длительный benchmark после каждой обычной UI-правки.

**Готовность:** целевые бюджеты выполнены либо документировано конкретное ограничение устройства и автоматически выбран безопасный low-профиль. Нет визуальных регрессий и устойчивого роста ресурсов.

## Устойчивость backend при наплыве пользователей

### Текущие данные и объёмы

- MongoDB служит восстанавливаемой read-моделью: `fleet_machines` хранит до 1425 машин, `public_snapshots` — общий снимок протокола, `fleet_earning_snapshots` — пятиминутную историю владельцев, `trade_transactions` и `trade_holders` — торговую историю и текущий состав держателей.
- В памяти одного Node.js-процесса находятся текущий trade state, короткоживущие Jupiter quotes, SSE listeners и одна объединяемая полная синхронизация public data.
- Nginx кэширует hashed-файлы из `/assets/` на год и `/nft/` на час. Изображения из `/fare-share/` и `/brand/` попадают под общий `no-cache`; общего CDN или API microcache в конфигурации нет.
- `overview` отдаёт максимум 100 лидеров. `walletFleet` не имеет pagination и теоретически может вернуть все 1425 машин одного владельца. История читает до 288/2016/8640 пятиминутных записей за 24 часа/7 дней/30 дней и группирует их примерно в 24–30 точек ответа.
- Trades ограничены 100 строками, holders — 250, candles — 1000 точек ответа. При этом `tokenSnapshot` и `candles` могут прочитать окно с неограниченным количеством сделок из MongoDB до формирования ограниченного ответа.
- Production-сборка занимает около 3 МБ файлов. Основные JS-части составляют примерно 362 КБ gzip; самый большой отдельный WebP — около 394 КБ.

Текущая оценка: обычный трафик приемлем, но готовность к большому всплеску не подтверждена. Главный риск создаёт не размер JSON, а связь публичных GET-запросов с полной Solana/DAS-синхронизацией, отсутствие кэша готового overview, общей защиты дорогих endpoints и предельной длины upstream-очередей.

### B-01. Отделить чтение сайта от полной Solana/DAS-синхронизации

**Статус:** реализовано. Публичные GET читают только MongoDB snapshot/read-модель, готовый overview сохраняется при фоновой синхронизации и кэшируется в процессе на 30 секунд, параллельное холодное чтение объединяется. HTTP допускает 15-секундный public cache и `stale-while-revalidate`; mint receipt больше не запускает полную синхронизацию, а DAS assets загружаются ограниченными пачками.

**Что:** убрать `sync(true)` из GET-запросов fleet/history, выполнять полную синхронизацию только одним фоновым процессом и сохранять готовый агрегированный overview. Отдавать overview из памяти или MongoDB с коротким TTL 15–30 секунд и `stale-while-revalidate`. DAS assets загружать ограниченными пачками в пределах контракта провайдера.

**Зачем:** посещение страницы не должно запускать `getProgramAccounts`, загрузку всех NFT, массовый `bulkWrite` и пересчёт snapshots.

**Было плохо:** последовательные посетители Garage могли запускать полную синхронизацию почти на каждый запрос. Одновременные overview-запросы делили одну синхронизацию, но каждый заново читал всю коллекцию машин и повторял одинаковую агрегацию.

**Станет хорошо:** публичные GET-запросы становятся дешёвыми и предсказуемыми, переживают временную недоступность RPC на последнем достоверном снимке, а стоимость Solana/DAS не растёт вместе с числом посетителей.

**Проверки и готовность:** focused tests public data; подтвердить, что fleet/history не вызывают RPC, параллельные overview используют один готовый результат, устаревший снимок явно содержит `observedAt`, а фоновая синхронизация корректно заменяет его.

### B-02. Ограничить входящий поток и внутренние очереди

**Статус:** отложено по решению владельца. Внешний burst и rate limits планируется обрабатывать правилами Cloudflare, поэтому дублирующие Nginx-лимиты сейчас не внедряются. Перед production нужно подтвердить, что origin нельзя обойти и что edge-правила отдельно защищают дорогие POST и SSE. Предельная длина внутренних Solana/Jupiter queues остаётся условной страховкой и возвращается в работу, только если B-08 покажет накопление запросов внутри приложения.

**Что:** добавить Nginx `limit_req`/`limit_conn` по группам маршрутов, отдельные лимиты для дорогих POST и SSE, максимальную длину Solana/Jupiter queues и быстрые ответы `429`/`503` при перегрузке. Лимиты должны учитывать корректно настроенный доверенный proxy и не объединять всех пользователей в один IP.

**Зачем:** перегруженный сервер должен отказать небольшой части запросов контролируемо, а не накапливать неограниченные promises, открытые соединения и память.

**Было плохо:** большинство публичных API не имело общего rate limit, а внутренние FIFO-очереди могли расти без жёсткой границы.

**Станет хорошо:** известен максимальный объём одновременно принятой работы; backend сохраняет health и обслуживает уже принятые запросы даже при всплеске или простом злоупотреблении API.

**Проверки и готовность:** focused tests очереди и лимитов, Nginx config test, короткий burst-тест подтверждает `429/503`, ограниченную память и восстановление после снятия нагрузки.

### B-03. Сузить публичный Solana RPC proxy

**Статус:** реализовано. Для каждого используемого frontend RPC-метода проверяются точная форма параметров и верхние границы. `getProgramAccounts` разрешает только scan Trainee PDA текущей Taxi-программы с обязательными `dataSize` и owner `memcmp`; account batches, DAS pagination, signatures и serialized transaction ограничены. Неиспользуемые формы и encoding отклоняются, размер upstream-ответа контролируется до полного чтения в память.

**Что:** ввести валидацию параметров отдельно для каждого разрешённого RPC-метода, запретить публичный произвольный `getProgramAccounts` либо требовать безопасные filters/dataSlice, ограничить размер upstream-ответа и закрыть методы, не нужные реальному frontend flow.

**Зачем:** один формально разрешённый RPC-вызов не должен заставлять backend скачивать и пересылать большой набор аккаунтов за счёт проекта.

**Было плохо:** проверялось имя метода и общий IP-лимит, но не реальная стоимость параметров и ответа. Тяжёлый запрос мог быть опасен даже при низком RPS.

**Станет хорошо:** proxy обслуживает только конкретные необходимые клиенту операции с известной верхней границей работы и трафика.

**Проверки и готовность:** contract tests каждого frontend RPC-вызова, отклонение широких запросов, проверка максимального request/response size и сохранение mint/claim/repair flow.

### B-04. Ограничить стоимость Trade read API

**Статус:** реализовано. `tokenSnapshot` и candles читают не более 20 001 последних исходных сделок, обрабатывают максимум 20 000 и явно возвращают `sourceTradesTruncated`, если окно пришлось усечь. Одинаковые token/candle reads объединяются и кэшируются на 10 секунд; кэш сбрасывается после записи trades, обновления token state или holders.

**Что:** заранее агрегировать 24-часовые token metrics и свечи либо жёстко ограничивать число исходных trades, читаемых одним запросом. Кэшировать одинаковые token/candles ответы на короткий срок и обновлять их после индексирования новых сделок.

**Зачем:** стоимость страницы Trade должна зависеть от фиксированного числа свечей, а не от количества операций популярного токена за весь временной диапазон.

**Было плохо:** API возвращал ограниченные ответы, но перед этим мог загружать в память все сделки за 24 часа или выбранное candle-окно.

**Станет хорошо:** latency и использование памяти остаются ограниченными при росте торговой активности; одинаковые посетители не повторяют одну агрегацию.

**Проверки и готовность:** focused trade tests на плотной synthetic history, сравнение свечей до/после, измерение количества прочитанных документов и p95 ответа.

### B-05. Ограничить срок хранения производных данных

**Что:** после подтверждения продуктового срока добавить TTL для `fleet_earning_snapshots` старше безопасного запаса над максимальными 30 днями, например 45 дней. Отдельно определить retention или архивирование `trade_transactions`, не удаляя данные, необходимые продукту и восстановлению.

**Зачем:** производный кэш не должен бессрочно увеличивать storage, размер индексов и стоимость обслуживания MongoDB.

**Было плохо:** пятиминутные earning snapshots и торговая история сохранялись без срока, хотя UI использует только ограниченные временные окна.

**Станет хорошо:** рабочий набор и индексы остаются ограниченными, а пользовательские 30-дневные графики сохраняются полностью.

**Проверки и готовность:** focused MongoDB integration test конкретного TTL-индекса, проверка границы 30/45 дней и документированное решение по trade retention.

### B-06. Ограничить и упростить SSE

**Что:** задать осознанный лимит Trade SSE connections, убрать предупреждение EventEmitter для нормальной рассчитанной ёмкости, использовать общий heartbeat вместо отдельного таймера при необходимости и корректно закрывать соединения при shutdown.

**Зачем:** каждое открытие Trade создаёт постоянное соединение, listener и heartbeat; их число должно быть наблюдаемым и ограниченным.

**Было плохо:** ёмкость SSE не была задана, а стандартный EventEmitter предупреждает уже после небольшого числа listeners.

**Станет хорошо:** известен предел одновременных live-клиентов, соединения не создают неконтролируемое число таймеров и корректно освобождаются.

**Проверки и готовность:** тест открытия/закрытия набора SSE-клиентов, отсутствие оставшихся listeners/timers, контролируемый отказ сверх лимита и успешное переподключение.

### B-07. Закрыть статический трафик кэшем

**Что:** выдать versioned изображениям `/fare-share/` и `/brand/` длительный `Cache-Control`, проверить gzip/Brotli для текстовых ресурсов и подключить CDN перед статикой, если измеренный launch-трафик превышает канал origin.

**Зачем:** новые посетители должны получать тяжёлые неизменяемые assets из browser/CDN cache, а не непосредственно с одного Nginx-сервера.

**Было плохо:** долгий immutable cache применялся только к `/assets/`; часть изображений обслуживалась с `no-cache`, CDN не был зафиксирован в конфигурации.

**Станет хорошо:** повторные загрузки почти не используют origin, а массовый первый заход распределяется CDN без изменения приложения.

**Проверки и готовность:** production headers, cold/warm network trace, отсутствие stale assets после versioned release и измерение origin bandwidth.

### B-08. Ввести измеримый load gate

**Что:** добавить короткие раздельные сценарии нагрузки для cached overview, Garage, history, Trade reads, quote и SSE. Собирать latency p50/p95/p99, error rate, active requests, queue depth, event-loop lag, RSS, Mongo latency и ошибки RPC/Jupiter. `/api/health` дополнить отдельной readiness-проверкой критичных зависимостей без дорогой on-chain синхронизации.

**Зачем:** без характеристик production-сервера и воспроизводимого теста нельзя назвать безопасное число одновременных пользователей.

**Было плохо:** build и функциональные тесты подтверждали корректность, но не пропускную способность и поведение при насыщении.

**Станет хорошо:** перед запуском известен фактический предел одного экземпляра, точка controlled rejection и конкретный bottleneck; масштабирование выполняется по измерению.

**Проверки и готовность:** один согласованный профиль обычного трафика и один короткий burst проходят установленный бюджет без роста очередей/памяти после окончания теста. Production endpoints для генерации нагрузки не используются.

Backend-очередь выполняется отдельно, начиная с устранения amplification публичных GET-запросов:

```text
B-01 read path и готовый overview
  → B-02 входные лимиты и bounded queues
  → B-03 безопасный RPC proxy
  → B-04 ограниченная стоимость Trade API
  → B-05 retention производных данных
  → B-06 SSE capacity
  → B-07 static cache/CDN
  → B-08 итоговый load gate
```

Если замер показывает, что этап не влияет на реальный bottleneck, он помечается как пропущенный с причиной. Следующий этап не должен опираться на неподтверждённую сложность предыдущего.
