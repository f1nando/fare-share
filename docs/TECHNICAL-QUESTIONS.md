# Технические вопросы проекта

Рабочий список вопросов для последовательной фиксации технических решений.

## Базовая сеть: Solana

- Проект работает в Solana, а не в Robinhood Chain/EVM.
- On-chain логика реализуется Solana-программами; изменяемое состояние хранится в PDA-аккаунтах.
- Нативная валюта сети и оплата транзакций — `SOL`.
- `$FARE` и токенизированные акции должны быть SPL-совместимыми токенами Solana. Конкретные Token Program и mint-адреса фиксируются отдельно.
- EVM-термины `ERC-20`, `ERC-721`, `ERC-4337`, `ERC-8056`, `Uniswap v4 hook`, `chainId`, Solidity, Foundry, OpenZeppelin, Anvil, viem и wagmi больше не являются частью архитектуры.
- Все ранее согласованные правила экономики, прочности, очереди и lazy accounting сохраняются, если ниже прямо не указано, что вопрос открыт заново из-за отличий Solana.
- Предыдущая Robinhood Chain/EVM-модель сохранена отдельно в `docs/evm-robinhood-chain/` и не смешивается с активными решениями Solana.

## Уже зафиксировано

- Фронтенд максимально простой: только необходимые рабочие экраны и действия.
- Вопросы ниже относятся только к технике реализации.
- Экономическая модель проекта описана отдельно и не пересматривается этим списком.

## Главные открытые вопросы — разбираем по порядку

- [x] **SOL-1. Источник торговых комиссий `$FARE` — временное решение** — `$FARE` запускается через pump.fun и после graduation использует canonical PumpSwap pool. Собственную комиссию 4%, Token-2022 `TransferFee` и Transfer Hook пока не реализуем. В экономику проекта поступает только фактический pump.fun Creator Fee. Его процент не фиксирован протоколом проекта и может меняться по правилам площадки и диапазону market cap; frontend не обещает пользователю постоянные 4%.
- [x] **SOL-1a. Pair asset запуска pump.fun — временное решение** — используем canonical пару `FARE/SOL`. Creator Fee поступает в SOL. Пользователю нужен SOL и для торговли, и для network fee; отдельный USDC для покупки `$FARE` не требуется. До дальнейших распоряжений вся схема split и конвертаций строится от фактически полученного SOL.
- [x] **SOL-1b. Split и конвертация Creator Fee** — фактически полученный SOL сначала делится по направлениям. 45% SOL используются для покупки `$FARE` в основной пул, 5% — для покупки `$FARE` в стажёрский пул, 20% — для покупки и немедленного burn `$FARE`, 20% — для прямой покупки stock-токенов без промежуточного `$FARE`, 10% — переводятся команде в SOL. Таким образом 70% Creator Fee создают покупательское давление на `$FARE`, а stock-доля не совершает лишний круг `SOL → FARE → stock`.
- [x] **SOL-1c. Получатель и сбор Creator Fees** — fee recipient задаём непосредственно как program-controlled PDA. Creator Fees не проходят через административный или backend-кошелёк. После поступления средств любой fee payer может permissionless запустить их обработку. До основного запуска обязательно проводим проверку на тестовом токене pump.fun: адрес принимается площадкой, средства действительно поступают PDA, а нужная claim/transfer-механика выполняется программой. Если площадка технически не поддерживает PDA-получателя, решение не подменяется молча — вопрос открывается повторно.
- [x] **SOL-1d. Формат pump.fun mint** — принимаем стандартный формат токена, создаваемого pump.fun. Не добавляем собственные Token-2022 extensions и не требуем административных mint/freeze-возможностей. Supply, decimals, Token Program, metadata и остальные параметры задаются поддерживаемым площадкой способом. Программа использует `$FARE` как обычный SPL-совместимый токен: покупает, хранит, переводит и сжигает только принадлежащие её vault токены. До основного запуска создаём тестовый токен и проверяем точные параметры mint, неизменяемость критичных полей, creator-fee ownership и прямое получение Creator Fees на PDA.
- [x] **SOL-2. Провайдер и состав stock-корзины** — используем только xStocks на Solana: `UBERx`, `TSLAx`, `GOOGLx` (Alphabet/Waymo) и `AMZNx` (Amazon/Zoox). Каждая позиция получает 5% Creator Fee. `LYFT` и `GRAB` исключены, потому что на дату проверки 2026-09-21 отсутствуют в официальном xStocks Assets API. Токены разных эмитентов не смешиваем; ticker или название без официального mint не считаются подтверждением.
- [x] **SOL-2a. Недоступная позиция корзины** — 5% Creator Fee для каждой позиции хранится в отдельном SOL-резерве, если официальный xStocks mint отсутствует, ликвидности недостаточно или swap не проходит по `minOut`. Резерв не перераспределяется другим акциям и не создаёт stock-долг перед NFT. После успешной будущей покупки фактически полученные токены входят только в новую расчётную серию.
- [x] **SOL-2b. Региональные ограничения xStocks** — frontend и условия использования явно сообщают, что пользователям из запрещённых xStocks юрисдикций нельзя пользоваться stock-функциями проекта. IP/геоблок, KYC, eligibility-voucher, denylist кошельков и on-chain ограничения не реализуем; программа остаётся permissionless и не определяет страну владельца. Пользователь сам подтверждает допустимость использования для своей юрисдикции. До публичного запуска отдельно проверяем с юристом, достаточно ли такого подхода для выбранных стран и способа распространения.
- [x] **SOL-3. Экономическое правило корпоративных событий** — начисление машины фиксируется в raw units xStocks. После расчёта этот raw amount принадлежит NFT экономически и следует текущему multiplier независимо от того, выполнен `claim` или нет. После `claim` тот же raw amount переходит в кошелёк пользователя. Новый пул формируется только из новых raw-токенов, фактически купленных следующей транзакцией; изменение multiplier отдельный пул не создаёт. Замена mint автоматически не выполняется.
- [x] **SOL-3a. Фиксация выплаты при `ScaledUiAmount`** — храним и переводим raw units без конвертации обязательства при `claim`. Frontend показывает `raw amount × current multiplier`, прочитанный из Token-2022 mint extension. Поэтому уже начисленная, но незаклеймленная награда автоматически отражает дивиденды, split и reverse split так же, как токены в кошельке.
- [x] **SOL-3b. Окно обновления multiplier** — специальную паузу до и после активации нового multiplier не вводим. `process_stock_swap`, `calculate_rewards` и `claim` продолжают работать. Raw-учёт остаётся корректным; небольшое возможное ценовое расхождение Jupiter-транзакции на границе corporate action принимается как менее существенное, чем получасовая остановка операций и дополнительная on-chain логика.
- [x] **SOL-4. Место покупки акций и маршрутизация** — используем Jupiter как единый агрегатор. Backend получает свежую котировку и формирует короткоживущий маршрут с нужными route-аккаунтами. Программа принимает только настроенный Jupiter program ID и проверяет stock mint на выходе, точный лимит входного SOL, `minOut`, deadline и отдельный nonce mint. Неуспешный маршрут не создаёт начисление и оставляет SOL в резерве соответствующей позиции. Один фиксированный AMM не используем, чтобы наличие всех четырёх xStocks не зависело от одного пула.
- [x] **SOL-5. Стандарт NFT-машин** — используем Metaplex Core Assets в официальной Core Collection проекта. Core Asset содержит владельца и NFT-метаданные, отображается в Phantom как коллекционный NFT и передаётся стандартной инструкцией Core. `weight`, прочность, checkpoints, `fareBase` и `claimable` хранятся в отдельном Machine PDA, привязанном к адресу Asset. Программа при действиях машины проверяет текущего owner и принадлежность Asset официальной коллекции. Token Metadata и Bubblegum не используем: первый создаёт лишние аккаунты и стоимость, второй добавляет DAS/Merkle proofs без необходимости при лимите 1425 NFT.
- [x] **SOL-6. Подключение кошелька и вход без seed-фразы** — в первой версии подключаем Phantom через Wallet Standard. Собственный embedded/passkey wallet не создаём, пользовательские ключи и данные восстановления backend не хранит. Пользователь сам выбирает доступный внутри Phantom способ создания и восстановления кошелька, включая поддерживаемый Phantom вход через Google/Apple и PIN либо обычную seed-фразу. Протокол зависит только от Solana public key и подписи, а не от способа входа в Phantom.
- [x] **SOL-6a. Оплата пользовательских транзакций** — пользователь самостоятельно оплачивает SOL network fee для mint, `claim`, ремонта, активации стажёра и `claim_trainee`. Backend не спонсирует пользовательские действия и не компенсирует их стоимость. Служебные `collect_fees` и `calculate_rewards` backend оплачивает только когда вызывает их сам; другой permissionless caller платит за себя.
- [x] **SOL-7. Формат `$FARE`** — используем стандартный SPL-совместимый mint, который создаёт pump.fun. Проект не добавляет собственные Token-2022 extensions и не сохраняет mint/freeze authority. Фактический Token Program и параметры фиксируются по результату обязательного тестового запуска до создания основного `$FARE`.
- [x] **SOL-8. Размер batch** — стартовый compile-time максимум равен 20 событиям на один `calculate_rewards`. Caller может запросить меньше, но больше 20 программа отклоняет. Backend отправляет последовательные транзакции, пока очередь не станет актуальной; 9000 событий потребуют 450 вызовов по 20. Перед mainnet худшие `MINT`, `REPAIR` и `EXPIRE` обязательно измеряются по compute units, размеру транзакции и account metas. Если 20 не помещаются стабильно, предел уменьшается до публикации immutable-программы; увеличение без необходимости не выполняем.
- [x] **SOL-9. Граница атомарности fee processing** — обработку делим на независимые permissionless-транзакции. `collect_fees` фиксирует только новый SOL, атомарно увеличивает резервы 70% `$FARE`, четырёх stock-позиций по 5% и переводит 10% команде. `process_fare_swap` одной Jupiter-покупкой меняет накопленный 70% резерв на `$FARE`, затем в той же транзакции распределяет фактически полученные токены в пропорции 45/70 для основного пула, 5/70 для стажёров и 20/70 для немедленного burn. Четыре независимых `process_stock_swap(mint)` покупают по одной позиции. Ошибка любой swap-транзакции откатывает только это направление; его SOL остаётся в резерве, а уже успешно обработанные направления не меняются.
- [x] **SOL-10. Transfer NFT во время глобальной паузы** — стандартный transfer Metaplex Core Asset остаётся разрешённым. Пауза блокирует инструкции Taxi и замораживает `protocolTime`, но не подключает Collection Freeze Plugin и не лишает владельца возможности отправить или продать NFT. Machine PDA, прочность и весь незабранный доход остаются привязаны к Asset и переходят новому owner; воспользоваться ими можно после `unpause`.
- [x] **SOL-11. Кто финансирует новые accounts** — первоначальные configuration, pool, vault и Core Collection accounts оплачивает команда при развёртывании. После запуска fee payer транзакции оплачивает rent-exempt deposit всех создаваемых ею accounts без компенсации: покупатель — Core Asset, Machine PDA и при необходимости новую страницу event queue; пользователь стажёра — Trainee PDA и нужные minute-bucket accounts; `claim`-caller — недостающие associated token accounts только для реально выплачиваемых mint; backend — служебные accounts, которые создаёт его транзакция. Это разовый депозит при создании, а не регулярная комиссия.

- [x] **0. Сбор, конвертация, расчёт и пользовательский Claim** — фоновые действия разделены на permissionless-инструкции: `collect_fees` резервирует поступивший SOL, `process_fare_swap` покупает и распределяет `$FARE`, `process_stock_swap(mint)` независимо покупает одну акцию, а `calculate_rewards` обрабатывает очередь и рассчитывает начисления. `claim(asset)` только выплачивает уже рассчитанный доход одной NFT-машины. Backend автоматически запускает фоновые инструкции, но любой кошелёк может сделать это самостоятельно и оплатить network fee в SOL.
- [x] **1. Границы одного расчёта** — при первом `calculate_rewards` фиксируются текущий пул и состав событий серии. Новые комиссии, mint, ремонты и поломки после этого относятся к следующему расчёту.
- [x] **2. Claim во время незавершённого расчёта** — разрешён. Пользователь получает только уже рассчитанную сумму; необработанные отрезки будут доступны после завершения серии `calculate_rewards`.
- [x] **3. Ремонт как событие** — создаётся запись с точным временем ремонта. Все расчёты до неё выполняются без машины, после неё машина участвует. Если серия `calculate_rewards` уже началась, событие относится к следующей серии.
- [x] **4. Нет активных машин** — комиссии остаются в пуле. Когда появляется одна активная машина, она получает весь доступный пул при следующем `calculate_rewards`.
- [x] **5. Обработка очереди** — `calculate_rewards` может отправить любой кошелёк, но компенсации network fee и бонуса нет. Fee payer полностью оплачивает транзакцию самостоятельно.
- [x] **6. Ремонт до полной поломки** — разрешён. Если осталось 2 часа, стоимость считается за 4 дня 22 часа; после ремонта прочность становится 5 дней, старая запись окончания становится неактуальной, новая запись добавляется в очередь.
- [x] **7. Частота `collect_fees`** — backend вызывает сбор при достижении минимальной суммы, заданной в его off-chain настройках. Solana-программа не запрещает более ранний permissionless-вызов. Суммы, которых недостаточно для допустимого swap, остаются в соответствующем PDA-vault до следующей попытки.

## Чек-лист

- [x] **1. Mint `$FARE`** — `$FARE` создаётся средствами pump.fun в стандартном формате площадки без собственных extensions и административных mint/freeze-возможностей проекта. Программа может сжигать `$FARE`, принадлежащий её vault, стандартной token-инструкцией. Точные адрес и параметры mint записываются в конфигурацию после тестового запуска.
- [x] **2. NFT-машины** — владение представлено Metaplex Core Asset из официальной коллекции проекта, а `weight`, прочность, расчётные checkpoints, `fareBase` и `claimable` — отдельным Machine PDA. Phantom показывает Asset как обычную NFT; живые игровые и финансовые показатели показывает frontend из Machine PDA. Старое решение ERC-721 отменено.
- [x] **3. Стажёрская программа** — на стажёров выделяется отдельный пул в размере **5%** комиссий; основной пул парка получает **45%**. Публичное кодовое слово публикуется в Twitter и намеренно доступно для поиска пользователями.
  - Пользователь вводит слово во frontend.
  - Backend проверяет актуальность слова и выдаёт персональный подписанный claim-вoucher.
  - Solana-программа проверяет ed25519-подпись backend, публичный ключ кошелька, `nonce`, срок действия, идентификатор deployment/cluster и `programId`.
  - Само кодовое слово в blockchain не передаётся и on-chain не хранится.
  - Ваучер нельзя повторно использовать или применить к другому кошельку.
  - Боты могут находить публичные слова; это допустимо, поскольку стажёры финансируются отдельным пулом и не затрагивают основную экономику.
- [x] **3a. Длительность стажёрской машины** — задаётся backend в подписанном ваучере от **1 часа до 7 дней**; начальное значение backend — 6 часов.
- [x] **3b. Формат стажёрской машины** — виртуальная машина без NFT. Solana-программа хранит PDA-запись по паре `wallet + campaignId` с датами начала/окончания, claim-checkpoint, весом и статусом. Такая машина не продаётся и не переводится. Один кошелёк может одновременно иметь машины нескольких разных кампаний.
- [x] **3c. Стажёрский пул** — стажёры делят только фактически накопленные 5% комиссий. Фиксированной выплаты и гарантированного дохода нет; при большом количестве стажёров доля каждого уменьшается.
- [x] **3d. Перенос накопленного дохода при продаже NFT** — накопленная claimable-доля принадлежит самой NFT и переходит новому владельцу вместе с ней. Свежесминченная NFT не получает комиссии, накопленные до её минта.
- [x] **4. Активность машины** — отдельной кнопки «На смену» нет. Машина активна от mint или ремонта до `activeUntil`. Permissionless-инструкция `calculate_rewards` обрабатывает события активности, а NFT можно передавать вместе с её состоянием и незабранным доходом.
- [x] **5. Границы расчётного пула** — при начале серии `calculate_rewards` текущие доступные активы фиксируются отдельно. Серия распределяет их по временным отрезкам и активным весам; новые поступления сохраняются для следующей серии.
- [x] **6. Учёт торговых комиссий** — вместо собственных 4% используем переменный pump.fun Creator Fee в SOL. Split выполняется до swap: 45% покупают `$FARE` для основного парка, 5% покупают `$FARE` для стажёров, 20% покупают и сжигают `$FARE`, 20% напрямую покупают stock-токены, 10% поступают команде в SOL.
- [x] **7. Покупка stock-токенов** — покупаем только xStocks на Solana через Jupiter. Permissionless-исполнение и backend-подписанный короткоживущий план сохраняются. Backend передаёт актуальный маршрут и route-аккаунты, а программа проверяет разрешённый Jupiter program ID и экономические границы swap. Неуспешная покупка оставляет SOL в отдельном резерве соответствующей позиции без перераспределения.
- [x] **8. Allowlist stock-токенов** — корзина ограничена четырьмя официальными Solana mint из xStocks Assets API: `UBERx` — `XsAsZLF4MmsvS1sDxRMrUz7REjHfwbC9UAMXSRBqgEB`; `TSLAx` — `XsDoVfqeBukxuZHWhdvWHBhgEHjGNst4MLodqsJHzoB`; `GOOGLx` — `XsCPL9dNWBMvFtTmwcCA5v3xWPSMEBCszbQdiLLq6aN`; `AMZNx` — `Xs3eBt7uRfJX8QUs4suhyU8p2M6DoUDrJyWBa8LLZsg`. На 2026-09-21 все четыре имели Jupiter-маршрут для тестовых размеров 0.1 и 1 SOL. Перед deployment адреса и маршруты проверяются повторно; один только ticker не принимается.
- [x] **9. Оплата транзакций** — network fee оплачивается в SOL отправителем: пользователь платит за свои действия, backend — за собственные автоматические вызовы, сторонний permissionless caller — за свой вызов. Спонсирования и компенсаций нет. Подключение выполняется через Phantom без собственного embedded wallet; ERC-4337 не используется.
- [x] **10. Выплаты** — `calculate_rewards` обновляет доход одного веса без массовых переводов владельцам. `claim(asset)` подписывает текущий owner и получает рассчитанный доход одной NFT. Максимум — 1425 NFT; массовых переводов нет.
- [x] **11. Округления** — остатки от округления переносятся в следующую эпоху и не сжигаются.
- [x] **12. Прочность машины и ремонт** — отказываемся от смен. Максимальная прочность каждой машины равна `X = 5 дней`, хранимых в секундах.
  - Прочность определяется временем от mint или последнего ремонта; `Claim()` на неё не влияет.
  - PDA состояния машины хранит `activeUntil`, а оставшееся время вычисляется по `Clock` sysvar и общему `protocolTime`, исключающему глобальные паузы.
  - Если прочность закончилась, машина больше ничего не получает, пока её не починят.
  - Ремонт всегда восстанавливает полные 5 дней, оплачивается в `$FARE`; уплаченные токены сжигаются.
  - Полная цена восстановления 5 дней равна 25% от выбранной базы `$FARE`-дохода самой машины. Фактическая цена умножается на долю недостающей прочности: `repairCost = fareBase × 25% × missingSeconds / 5 дней`.
- [x] **13. История расчётных отрезков и окно `X` дней** — храним общую историю рассчитанных временных отрезков в кольцевом буфере минимум за последние `X = 5 дней`. В каждой записи есть время начала, время окончания, доход на один вес и общая сумма, начисленная всем машинам за этот отрезок. Отдельную историю отрезков для каждой NFT не создаём: её активные границы, вес и единый `claimable` хранятся в состоянии самой машины.
- [x] **14. Точная формула ремонта** — ремонт всегда восстанавливает машину до полной прочности `X = 5 дней`. Стоимость считается только за недостающий срок: `repairCost = fareBase × 25% × missingSeconds / MAX_DURABILITY`. При базе `100 FARE` полный ремонт стоит `25 FARE`, а восстановление одного дня — `5 FARE`. Выплаты за период простоя задним числом не начисляются.
- [x] **15. Активные машины** — активна любая сминченная NFT с прочностью больше нуля. Машина с нулевой прочностью исключается из суммы весов; после ремонта сразу возвращается в активный вес.
- [x] **16. Ремонт и начисления** — ремонт действует с точного времени Solana-транзакции. Машина возвращается в активный вес с этой секунды, но доход становится доступен для `claim` только после обработки repair-события инструкцией `calculate_rewards`.
- [x] **17. Emergency-функции** — используем одну глобальную `pause`, rescue случайно отправленных поддерживаемых токенов по отдельно согласованным правилам и замену разрешённых внешних program/mint-адресов. Во время паузы блокируются изменяющие состояние инструкции Taxi, включая mint, ремонт, стажёрскую активацию, `collect_fees`, `process_fare_swap`, `process_stock_swap`, `calculate_rewards` и `claim`; чтение Solana accounts и прямой transfer Metaplex Core Asset остаются доступными.
- [x] **18. Upgradeability** — перед production программа развёртывается через стандартный upgradeable loader для проверки, затем upgrade authority отзывается, чтобы логика стала immutable. Изменяемыми остаются только явно разрешённые значения конфигурационного PDA.
- [x] **19. On-chain стек** — Rust + Anchor. Anchor используем для account validation, IDL, сборки, тестов и deployment scripts. Вызовы Token Program/Token-2022, NFT-программы и swap venue выполняются через CPI только там, где это требуется.
- [x] **20. Frontend** — React + Vite + TypeScript. Интерфейс остаётся минимальным и общается с Solana RPC и программой через сгенерированный IDL/client.
- [x] **21. Backend** — Node.js/TypeScript + MongoDB для индексации событий, истории и статистики. Blockchain остаётся источником истины, MongoDB используется как быстрый read-слой.
- [x] **22. Blockchain data/indexer** — собственный indexer на Node.js/TypeScript + MongoDB, с периодической сверкой и восстановлением по blockchain. Blockchain остаётся источником истины.
- [x] **23. Wallet и Solana-интеграция** — используем актуальный `@solana/kit`, React bindings и Wallet Standard. В первой версии подключаем Phantom и не внедряем собственный embedded wallet. Backend не получает пользовательские ключи и не управляет восстановлением доступа. Старые `viem`/`wagmi` не используются.
- [x] **24. Deployment и окружения** — используем Anchor/Solana CLI scripts и `.env` для RPC, program IDs и публичных параметров. CI запускает тесты и сборку, но не деплоит. Публикация в devnet/mainnet-beta выполняется вручную и требует отдельного разрешения.
- [x] **25. Тестовая среда** — быстрые unit-тесты Rust, Anchor tests и локальный `solana-test-validator`/LiteSVM; затем devnet smoke перед публикацией. В mainnet-beta не деплоим без отдельного разрешения.

## Дополнительная модель начислений

- [x] **26. Lazy accounting выплат** — используем общий доход на единицу веса. PDA каждой NFT хранит checkpoint, `activeUntil`, вес и `claimable`; при `claim` выполняется небольшой расчёт только этой машины.
- [x] **27. Динамическая активность машин** — используем хронологическую очередь без перебора 1425 NFT. Mint и repair добавляют будущие события, а `calculate_rewards` проходит очередь по времени и меняет `totalActiveWeight`. Старое окончание после ремонта остаётся stale-событием с прежней версией машины.
- [x] **28. Публичные функции выплат** — используем три функции:
  - `collect_fees` — фиксирует новый SOL и раскладывает его по внутренним резервам без swap. `process_fare_swap` и отдельные `process_stock_swap` выполняют покупки через Jupiter. Все инструкции может отправить любой кошелёк; backend делает это автоматически.
  - `calculate_rewards` — продвигает очередь на ограниченное число событий. Инструкцию может отправить любой кошелёк; backend последовательно обрабатывает очередь.
  - `claim` — пользователь забирает доход одной своей машины.
- [x] **29. Способ начисления всем машинам** — `calculate_rewards` сохраняет рассчитанные временные отрезки и увеличивает общий счётчик дохода одного веса в PDA состояния пула. У PDA каждой NFT записываются показания этого счётчика в начале и конце активного периода, вес, уже выплаченная граница и единый `claimable`. При `claim` программа вычитает начальное показание из конечного и умножает разницу на вес, поэтому не перебирает всю историю и все NFT.
- [x] **30. Новые комиссии во время расчёта** — комиссии, собранные после начала серии `CalculateRewards()`, относятся к следующей серии и не меняют зафиксированный текущий пул.
- [x] **31. Что считается одним событием** — одно изменение состояния одной NFT (`MINT`, `REPAIR` или `EXPIRE`) является отдельным событием и отдельным шагом `calculate_rewards`. События никогда не объединяются, даже если несколько машин изменились в одну секунду. При одинаковом времени промежуток равен нулю, а порядок задаёт `eventNumber`. Backend передаёт необходимые PDA машин для ближайшего batch, а программа сверяет их с вершиной очереди.
- [x] **32. Claim во время незавершённой очереди** — разрешён; пользователь получает только уже рассчитанный доход, а оставшаяся часть станет доступна после продвижения очереди.
- [x] **33. Несколько `collect_fees` подряд** — комиссии складываются в общий текущий пул. `calculate_rewards` распределяет весь доступный баланс; время отдельных сборов не учитывается.
- [x] **34. Ошибка покупки stock-токена** — неудачный `process_stock_swap(mint)` откатывается целиком, а непотраченный SOL остаётся за конкретным stock mint в `stockReserve` и используется при следующей попытке. Остальные направления не откатываются.
- [x] **35. Расчёт при пустом пуле** — `calculate_rewards` продвигает очередь даже при нулевом пуле. Пройденные отрезки фиксируются с нулевым доходом и не получают будущие деньги задним числом.
- [x] **36. Награда за служебные инструкции** — компенсации и бонуса нет. Fee payer инструкции `collect_fees` или `calculate_rewards` самостоятельно оплачивает network fee в SOL.
- [x] **37. Возвращение активной машины** — если в пуле накопились деньги, а затем снова появилась только одна активная машина, она получает весь доступный пул при следующем `CalculateRewards()`.
- [x] **38. Ремонт как событие расчёта** — при ремонте старая запись окончания прочности становится неактуальной, а в очередь добавляется новая запись окончания через 5 дней. При mint добавляется аналогичная запись начала активности/окончания прочности. При обработке события машина добавляется или исключается из активного расчёта.
- [x] **39. Границы одного расчёта** — в начале серии `CalculateRewards()` фиксируются текущий пул, время начала и время окончания расчёта. Новые комиссии и события, появившиеся после начала серии, относятся к следующей серии.
- [x] **40. Начисление без перебора машин** — вместо записи дохода в каждую активную NFT обновляем общий счётчик дохода одного веса. Конкретная NFT получает сумму по разнице показаний за свой активный период при `Claim()` или при обработке события изменения её состояния.
- [x] **41. Размер шага расчёта** — `calculate_rewards` принимает `limit`, но программа ограничивает его compile-time максимумом 20 событий. Перед mainnet измеряем compute units, размер транзакции и количество writable accounts для худших `MINT`, `REPAIR`, `EXPIRE`; при необходимости уменьшаем константу до публикации immutable-программы.
- [x] **42. Физический баланс и расчётный остаток** — SPL-токены остаются в program-controlled vaults до пользовательского `claim`, но уже обработанная часть резервируется внутренним учётом и не участвует в следующих расчётах.
- [x] **43. Новые комиссии во время частичного расчёта** — PDA пула отдельно хранит зафиксированный остаток текущей серии и поступления следующей серии. `collect_fees` во время незавершённого расчёта не увеличивает текущий остаток; после завершения новые поступления становятся пулом следующей серии.
- [x] **44. Автоматическое закрытие периода при ремонте** — транзакция ремонта сразу записывает событие с точным временем и новый срок окончания через 5 дней, даже если расчётная очередь отстаёт. Когда `CalculateRewards()` хронологически доходит до этого события, он закрывает старый период, добавляет его рассчитанный доход в `claimable` NFT и фиксирует текущее показание дохода одного веса как начало нового периода. До обработки события пользователь может забрать только ранее рассчитанный доход. Старые периоды отдельно не хранятся.
- [x] **45. Повторный ремонт при отставшей очереди** — повторные ремонты разрешены, даже если `CalculateRewards()` ещё не обработал предыдущее событие ремонта. Каждое событие сохраняется с точным временем и обрабатывается по хронологии. Каждый ремонт восстанавливает прочность до 5 дней, оплачивается только фактически недостающая на этот момент прочность и делает предыдущую будущую поломку неактуальной. Итоговая поломка назначается через 5 дней после последнего ремонта.
- [x] **46. Право на ремонт после transfer** — ремонт может вызвать только текущий владелец Solana NFT asset. Marketplace/delegate-полномочия сами по себе не дают права ремонтировать машину. Программа проверяет текущего owner через выбранную NFT-программу; состояние, очередь и накопленный доход привязаны к адресу asset и переходят вместе с ним.
- [x] **47. Цена ремонта при отставшей очереди** — ремонт не ждёт расчётную очередь. `fareBase` включает только уже рассчитанный `$FARE`-доход NFT после прошлого mint/ремонта, а frontend показывает `calculatedUntil`. Нерассчитанный доход не входит в цену текущего ремонта и после обработки старого периода остаётся claimable, не загрязняя новую ремонтную базу.
- [x] **48. Нет рассчитанного дохода для ремонта** — если после прошлого mint/ремонта `fareBase == 0`, стоимость ремонта равна нулю независимо от потерянной прочности. Искусственная оценка нерассчитанных периодов не выполняется.
- [x] **49. Stock-токены в распределении** — в расчётную серию попадают только фактически купленные Solana stock-токены, уже находящиеся в program-controlled token accounts. Неудавшаяся покупка оставляет `$FARE` в `stockReserve` и не создаёт долг перед NFT.
- [x] **50. Хранение прочности** — для машины хранится точное время поломки `activeUntil`, а не отдельно уменьшаемое количество оставшихся секунд. Оставшаяся прочность вычисляется как `max(activeUntil - currentTime, 0)`. `Claim()` не меняет `activeUntil`; ремонт устанавливает `activeUntil = repairTime + 5 дней` и создаёт соответствующее событие поломки.
- [x] **51. Точная граница поломки** — активный период хранится как полуоткрытый интервал `[activeFrom, activeUntil)`. Машина активна только при `timestamp < activeUntil`; при `timestamp >= activeUntil` она уже сломана. Так машина работает ровно 5 дней без дополнительной секунды и двойного начисления на границе.
- [x] **52. Начало дохода после mint** — новая NFT начинает участвовать с точного времени минта и не получает доход за более ранние отрезки. Она может делить уже находящийся в PDA-vault нераспределённый пул за время после минта, потому что время поступления отдельных комиссий не учитывается. Если расчётная серия началась до минта, событие относится к следующей серии.
- [x] **53. Transfer NFT и расчётная очередь** — передача NFT не создаёт событие расчёта, потому что вес, `activeUntil` и участие машины не меняются. `claimable`, текущий активный период, прочность и очередь будущих событий принадлежат NFT и переходят новому владельцу. После transfer только новый владелец может вызвать `Claim()` или ремонт; результат конкурирующих действий определяется обычным порядком транзакций в blockchain.
- [x] **54. Размер одного Claim** — `claim(asset)` обрабатывает ровно одну NFT и доступен только её текущему владельцу. Программа не обходит все NFT кошелька и не предоставляет `claim_all` в первой версии. Во frontend каждая машина имеет отдельную кнопку получения дохода.
- [x] **55. Атомарность Claim** — выплата одной NFT выполняется целиком. Если перевод любого начисленного актива завершается ошибкой, вся транзакция откатывается: ранее выполненные в ней переводы отменяются, а `claimable` и контрольные значения NFT не изменяются. Частичные выплаты и отдельные долги по токенам не создаются.
- [x] **56. Область аварийной паузы** — программа блокирует свои изменяющие состояние инструкции и замораживает `protocolTime`. Прямой transfer Metaplex Core Asset через внешнюю Core-программу остаётся разрешённым; Collection Freeze Plugin не используем.
- [x] **57. Округление разных активов** — расчёты выполняются целочисленно с повышенной внутренней точностью, а переводы округляются вниз до минимальной raw-единицы конкретного SPL-токена. Остаток каждого mint хранится отдельно и переносится в следующую серию этого же актива.
- [x] **58. Одновременные `calculate_rewards`** — вызывающий не передаёт ожидаемый курсор. Каждая транзакция читает актуальную позицию очереди при исполнении и обрабатывает следующий безопасный batch, поэтому последовательно исполненные транзакции продолжают друг друга без двойного начисления.
- [x] **59. Оплата permissionless-вызовов** — протокол не компенсирует network fee и не выплачивает бонусы за `collect_fees` или `calculate_rewards`. Backend выполняет их за свой SOL; другой fee payer может сделать то же самое за собственный SOL.
- [x] **60. Частота `calculate_rewards`** — backend раз в минуту бесплатно читает очередь через RPC. Если есть готовые события, он отправляет последовательные транзакции максимум по 20 событий до актуального состояния. При отсутствии работы транзакция не отправляется.
- [x] **61. Порог `collect_fees`** — минимальная сумма для автоматической транзакции хранится только в backend. On-chain порога нет: любой fee payer может отправить инструкцию раньше за собственный SOL. Слишком маленькая сумма остаётся в резерве.
- [x] **62. Веса stock-корзины** — четыре xStocks-позиции получают по 25% stock-бюджета, то есть по 5% Creator Fee. Недоступная доля остаётся в собственном SOL-резерве и не увеличивает доли остальных позиций.
- [x] **63. Простая защита цены stock-покупок** — не добавляем собственный on-chain oracle или TWAP. Backend формирует короткоживущий план по свежей котировке Jupiter с допуском 5%. Неуспешная покупка не блокирует другие направления и оставляет сумму в резерве соответствующей позиции.
- [x] **64. Backend signer** — один отдельный технический Solana keypair без средств подписывает стажёрские ваучеры и swap-планы. Типы сообщений разделены и включают nonce, deadline, deployment domain и `programId`. Подпись проверяется через ed25519 verification instruction; ключ не управляет программой и не хранит казну.
- [x] **65. Административное управление** — multisig не используется. Один административный Solana pubkey управляет `pause/unpause`, заменой backend signer, разрешёнными внешними program/mint-адресами и rescue. Передача роли выполняется в два шага через поля `pendingAdmin` и отдельную инструкцию принятия; EVM `Ownable2Step` не используется.

## Осталось уточнить

Разбираем по порядку. Пункты с пометкой «заказчик» можно отложить в конец.

- [x] **66. Структура хронологической очереди** — используем min-heap в одном или нескольких PDA-аккаунтах с ключом `timestamp + eventNumber`. При ремонте старое окончание помечается неактуальным и позже извлекается с вершины. Каждый pop расходует один шаг bounded batch. Backend читает вершину и передаёт программе PDA машин, необходимые для обработки; программа не доверяет переданному порядку и валидирует каждое событие.
- [x] **67. База `$FARE` для цены ремонта** — исторический расчёт через доход всех машин, бинарный поиск и текущий `totalActiveWeight` отменён. `fareBase` равен фактически рассчитанному `$FARE`-доходу самой NFT после последнего mint/ремонта. Полная цена восстановления равна 25% этой суммы, а фактическая цена дополнительно умножается на долю недостающей прочности. `Claim()` не обнуляет ремонтную базу; после ремонта она начинается заново.
- [x] **67a. Актив для оценки ремонта** — стоимость ремонта выражается и оплачивается только в `$FARE`. Базой служит `$FARE`-доход самой ремонтируемой NFT за выбранный период; акции остаются отдельным бонусным доходом.
- [x] **67b. Процент и пропорция ремонта** — полное восстановление пяти дней стоит 25% от `fareBase`. Неполная потеря прочности оценивается пропорционально секундам: один недостающий день равен 20% полной цены ремонта, то есть 5% от `fareBase`.
- [x] **67c. Отображение цены ремонта** — frontend/backend читает PDA машины и глобального расчёта через RPC и общей client-функцией вычисляет `fareBase`, недостающие секунды, полную и фактическую цену, а также `calculatedUntil`. На Solana отдельная on-chain view-функция не требуется.
- [x] **67d. Цена в транзакции ремонта** — отдельный `maxRepairCost` в первой версии не используется. Frontend показывает свежий расчёт по account data, а инструкция `repair` заново вычисляет и списывает авторитетную сумму внутри программы.
- [x] **68. Периоды без активных машин** — секунды с `totalActiveWeight == 0` не расходуют расчётный пул и не входят в распределяемую длительность. Деньги ждут следующего отрезка с активными машинами. Если после пустого периода появляется одна машина, она получает весь ожидающий пул; если появляется несколько, пул делится между ними по весам активных отрезков.
- [x] **69. Изоляция стажёрского пула** — основной парк и стажёры используют независимые PDA-пулы, общий вес, показатель дохода одного веса, курсор и очередь. Одна инструкция `calculate_rewards(group)` обрабатывает безопасный batch выбранной группы. Стажёрские minute buckets не задерживают расчёт NFT и не затрагивают 45% основного пула.
- [x] **69a. Масштабирование стажёрских событий** — используем минутные корзины. Активация начинается со следующей полной минуты и заканчивается согласно длительности ваучера. Все кошельки одной стартовой минуты увеличивают общий `weightDelta` одной корзины; одинаковые минуты окончания также объединяются. Отдельные события для каждого стажёра не создаются. Для каждой пары `wallet + campaignId` сохраняются личные `activeFrom`, `activeUntil` и claim-checkpoint. Основная NFT-очередь сохраняет точность до секунды.
- [x] **69b. Ограничения стажёрских ваучеров** — одно кодовое слово соответствует `campaignId`; один кошелёк может активировать машину каждой кампании ровно один раз. Несколько машин разных кампаний могут быть активны на одном кошельке одновременно. Глобальной квоты участников нет; бесконечные новые кошельки экономически ограничены отдельным 5% пулом, а backend rate limit защищает только API.
- [x] **69c. Длительность стажёра из backend-ваучера** — ваучер содержит длительность в целых минутах. Программа вычисляет `activeFrom` как следующую полную минуту и `activeUntil = activeFrom + durationMinutes × 60`, затем меняет соответствующие minute-bucket PDA. Изменение backend-настройки влияет только на новые активации.
- [x] **69d. Границы длительности стажёра** — программа принимает подписанную длительность от 60 минут до 7 дней включительно. Backend по умолчанию выдаёт 6 часов.
- [x] **69e. Claim стажёрской машины** — `claim_trainee(campaignId)` обрабатывает одну виртуальную машину пары `wallet + campaignId`. Доход разных кампаний не перебирается и не смешивается; массовый claim в первой версии отсутствует.
- [x] **70. Где удерживается торговая комиссия** — до дальнейших распоряжений комиссия определяется bonding curve/canonical PumpSwap pool платформы pump.fun. Собственных 4% нет. Проект получает только Creator Fee в SOL по действующим правилам площадки и делит фактически полученную сумму по схеме SOL-1b.
- [x] **71. Burn и операционные 10%** — `collect_fees` переводит команде 10% нового SOL. Накопленные 70% меняются одной транзакцией `process_fare_swap`; 20/70 фактически полученного `$FARE` сжигаются через Token Program CPI в той же транзакции. Если swap, распределение или burn завершается ошибкой, вся `process_fare_swap` откатывается и SOL остаётся в резерве.
- [x] **72. Corporate actions и `ScaledUiAmount`** — программа считает обязательства и переводы в неизменных raw units. Frontend всегда применяет текущий multiplier из Token-2022 mint extension. Уже начисленная награда следует multiplier до и после `claim`; отдельного пула от multiplier не возникает. ERC-8056 не используется.
- [x] **73. Время во время глобальной паузы** — пауза замораживает `protocolTime`: машины не теряют прочность и не получают новые награды. PDA конфигурации хранит время начала текущей паузы и суммарную длительность завершённых пауз, поэтому обновлять все NFT не нужно.
- [x] **74. Параметры подписанного swap-плана** — план содержит точные stock mint, `amountIn`, `minOut`, `deadline`, nonce, deployment domain и `programId`. Ed25519-подпись действует 10 минут, slippage по умолчанию 5%. Для каждого stock mint ведётся отдельный nonce; первый успешный план увеличивает его и делает конкурирующие планы с прежним nonce недействительными.
- [x] **75. Mint NFT** — продажа оплачивается SOL, имеет фиксированные тиражи и веса, не ограничивает количество NFT на кошелёк и открывается сразу для всех ручной инструкцией `start_sale`. Точные цены в lamports задаются перед стартом по согласованным долларовым ориентирам.
- [x] **75a. Тиражи и веса NFT** — всего 1425 машин: 1000 «Эконом» с весом 1, 300 «Комфорт» с весом 3, 100 «Бизнес» с весом 10 и 25 «Легенда» с весом 30. Максимальный общий вес равен 3650. Доли классов при полностью активном тираже составляют примерно 27.40%, 24.66%, 27.40% и 20.55% соответственно.
- [x] **75b. Цены mint** — сохраняем долларовые ориентиры старой модели: `$49` для «Эконом», `$129` для «Комфорт», `$399` для «Бизнес» и `$1099` для «Легенда». Непосредственно перед открытием продажи команда один раз переводит эти значения по актуальному курсу в точные lamports SOL и записывает их в configuration PDA. После `start_sale` цены замораживаются до конца mint; oracle и автоматический пересчёт во время продажи отсутствуют.
- [x] **75c. Лимит на кошелёк** — лимита нет. Один кошелёк может минтить любое количество NFT любого класса, пока не исчерпан лимит этого класса и общий тираж. Один вызов mint создаёт одну NFT; отдельный on-chain счётчик покупок кошелька не храним.
- [x] **75d. Доступ к продаже** — продажа открывается сразу для всех. После `start_sale` любой кошелёк может минтить машины по общим правилам. Allowlist, presale, персональные ваучеры и отдельный ранний этап отсутствуют.
- [x] **75e. Момент открытия продажи** — администратор вручную вызывает `start_sale` после проверки точных цен, метаданных и frontend. Автоматического открытия по timestamp нет.
- [x] **76. Метаданные NFT** — готовые изображения и JSON загружаются в Arweave через Irys, показываются сразу после mint и не меняются. Reveal отсутствует; окончательные URI проверяются до блокировки метаданных и запуска продажи.
- [x] **76a. Неизменяемость и reveal** — до запуска готовы изображения и JSON всех машин. Каждая NFT сразу получает окончательный URI; общей скрытой картинки и последующего reveal нет. На официальную Metaplex Core Collection устанавливаем `ImmutableMetadata`, поэтому имена и URI коллекции и входящих в неё Assets нельзя заменить после выпуска. Динамическую прочность, доход и ремонт по-прежнему читаем из Machine PDA, а не из metadata.
- [x] **76b. Хранилище файлов** — изображения и metadata JSON размещаем в Arweave через Irys. Перед `start_sale` проверяем доступность каждого JSON, ссылки на изображения и соответствие класса/признаков. Обычный сервер/CDN и IPFS pinning не являются основным источником NFT-файлов.
- [x] **77. Состав пользовательской выплаты** — фиксированного соотношения `$FARE`/акций по стоимости нет. `claim` переводит фактически начисленные raw amounts `$FARE` и каждого из четырёх xStocks отдельно. Slippage, изменение цены или временно неудавшаяся покупка одной позиции не вызывают ребалансировку, дополнительный swap или долг перед NFT и не меняют начисления остальных активов.
- [x] **78. Rescue** — единственный admin может вывести любые активы из program-controlled vault для оперативной реакции на инцидент, но инструкция доступна только во время глобальной паузы.
- [x] **78a. Активы, доступные Rescue** — единственный admin может вывести из program-controlled vault SOL, `$FARE`, любой из четырёх xStocks и посторонние SPL-токены. Программа не ограничивает Rescue только неучтённым остатком. Это намеренно доверенная аварийная возможность: компрометация admin-ключа позволяет вывести пользовательские резервы и рассчитанные, но ещё не полученные выплаты.
- [x] **78b. Предусловие Rescue** — перед каждым Rescue глобальная пауза уже должна быть активна; иначе инструкция отклоняется. Pause и Rescue являются двумя отдельными административными транзакциями. Пока действует пауза, mint, ремонт, claim, обработка комиссий и расчёт наград не могут параллельно менять vault и обязательства.
- [x] **79. Заменяемые внешние адреса** — `$FARE`, отдельные xStocks mint и Jupiter Program ID заменяются только во время паузы; team account и backend signer могут быть заменены admin без остановки протокола.
- [x] **79a. Замена `$FARE` mint** — admin может указать новый официальный `$FARE` mint только при активной глобальной паузе. В обычном режиме инструкция отклоняется. Новый адрес не считается тем же активом автоматически и не переименовывает старые raw-балансы или обязательства; их обработка определяется отдельным решением миграции.
- [x] **79b. Старый `$FARE` после замены** — замена фиксирует границу по замороженному `protocolTime`. Старый нераспределённый пул рассчитывается только за период до этой границы, а уже рассчитанные и позднее закрытые старые начисления выплачиваются прежним mint. Доход после границы, новая ремонтная база и оплата ремонтов используют новый mint. Программа хранит один legacy FARE vault/набор обязательств и запрещает следующую замену, пока его нераспределённый пул и обязательства не равны нулю.
- [x] **79c. Замена xStocks mint** — admin может во время глобальной паузы заменить mint одной конкретной корзинной позиции. По замороженному `protocolTime` старый пул этой позиции закрывается для новых поступлений, но продолжает рассчитываться и выплачиваться прежним mint; будущие swaps и начисления позиции используют новый mint. Остальные три позиции не меняются. У каждой позиции один legacy slot; следующая её замена запрещена до нулевого старого пула и обязательств.
- [x] **79d. Замена Jupiter Program ID** — Configuration PDA хранит ровно один разрешённый Jupiter Program ID. Admin может заменить его только при активной глобальной паузе. После обновления CPI в старую программу отклоняется; одновременно разрешённый список старых и новых версий не поддерживается.
- [x] **79e. Замена team account** — admin может без глобальной паузы заменить адрес, которому `collect_fees` переводит будущие 10% SOL. Изменение применяется со следующего успешного сбора, не перемещает уже отправленный SOL и не меняет основные, стажёрские или stock-резервы.
- [x] **79f. Замена backend signer** — admin может без глобальной паузы записать новый публичный ключ backend signer. С этого момента программа принимает swap-планы и стажёрские ваучеры только с подписью нового ключа; все неиспользованные сообщения старого ключа становятся недействительными независимо от их прежнего deadline. Signer не получает admin- или Rescue-права.
- [x] **80. Восстановление backend/indexer** — backend работает только с finalized-состоянием, после перезапуска перечитывает актуальные PDA, безопасно повторяет jobs благодаря on-chain проверкам, а собственные off-chain данные защищает ежедневной резервной копией управляемой MongoDB.
- [x] **80a. Уровень подтверждения backend** — backend обрабатывает события и запускает связанные фоновые операции только после commitment `finalized`. Статус `confirmed` допускается только как промежуточная индикация во frontend и не создаёт окончательную MongoDB-запись. Поэтому backend не реализует откат бизнес-событий из временной Solana fork.
- [x] **80b. Перезапуск и пропущенное время** — при старте backend заново читает актуальные configuration, pool, reserve и queue PDA и решает, какие служебные инструкции нужны сейчас. Пропущенные транзакции и slots по одной не воспроизводятся. Денежное состояние, расчётные курсоры и очередь восстанавливаются из Solana; MongoDB не может переопределить on-chain значения.
- [x] **80c. Повторный запуск job** — денежную идемпотентность обеспечивает Solana-программа, а не MongoDB-lock. Swap-план имеет одноразовый nonce; `collect_fees` учитывает только ещё не распределённый вход; `calculate_rewards` всегда читает актуальный on-chain курсор. Повторная отправка либо безопасно отклоняется устаревшим состоянием, либо выполняет следующую действительно доступную работу, но не повторяет уже проведённую операцию.
- [x] **80d. Резервная копия MongoDB** — production использует управляемую MongoDB с автоматической ежедневной резервной копией. Backup восстанавливает кампании, backend-настройки, nonce и служебный кэш, но не считается источником истины для NFT, резервов или начислений: финансовое состояние всегда повторно читается из finalized Solana PDA.
- [ ] **81. Финальный Solana batch limit** — измерить compute units, размер транзакции и количество account metas для худших `MINT`, `REPAIR`, `EXPIRE`; подтвердить безопасный лимит до mainnet-beta.
- [x] **82. Средства от продажи NFT** — полная зафиксированная цена mint в SOL сразу переводится на текущий team account. Эти средства не входят в Creator Fee, основные/стажёрские/stock-пулы и не создают доход машин. Fee payer отдельно оплачивает network fee и rent-exempt deposit создаваемых NFT/Machine accounts.
- [x] **83. Вторичная продажа NFT** — Metaplex Core Royalties plugin не устанавливаем. Проект не получает процент со вторичной продажи или передачи машин; экономика вознаграждений зависит от Creator Fees `$FARE`, а не от NFT royalties.
- [x] **84. Прямое сжигание NFT** — Core Asset остаётся свободно сжигаемым владельцем. Backend отслеживает finalized burn и вызывает permissionless `cleanup_burned_machine`, но любой caller может сделать это раньше. Программа проверяет burned/uninitialized состояние Core Asset и создаёт `BURN`-событие на текущий `protocolTime`; историческую секунду внешнего burn не восстанавливаем. При обработке события машина исключается из активного веса, прежнее `EXPIRE` становится stale, а все её незабранные `$FARE`/xStocks возвращаются в соответствующие следующие пулы. Machine PDA остаётся как закрытая запись, чтобы не вводить отдельное правило возврата rent.
- [x] **84a. Тираж после burn** — burn не уменьшает class minted counter и не освобождает место в тираже. Лимиты `1000 / 300 / 100 / 25` относятся к количеству когда-либо созданных машин. Поэтому после сжигания одной из полностью выпущенных 25 «Легенд» в обращении остаётся 24, а выпустить 26-ю нельзя.
- [x] **85. Завершение NFT sale** — после одноразового `start_sale` отдельной административной функции permanent close или повторного открытия нет. Продажа каждого класса заканчивается при достижении его minted cap; глобальная пауза может временно блокировать mint вместе с остальными проектными инструкциями, но не изменяет тиражи и статус старта.
