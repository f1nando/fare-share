# Технические вопросы проекта

Рабочий список вопросов для последовательной фиксации технических решений.

## Уже зафиксировано

- Фронтенд максимально простой: только необходимые рабочие экраны и действия.
- Вопросы ниже относятся только к технике реализации.
- Экономическая модель проекта описана отдельно и не пересматривается этим списком.

## Главные открытые вопросы — разбираем по порядку

- [x] **0. Сбор, расчёт и пользовательский Claim** — действия разделены на три permissionless-функции. `CollectFees()` забирает комиссии, выполняет доступные покупки stock-токенов и пополняет пулы. `CalculateRewards()` обрабатывает очередь и рассчитывает начисления. `Claim(tokenId)` только выплачивает уже рассчитанный доход одной NFT. Backend автоматически вызывает первые две функции, но любой адрес может вызвать их самостоятельно и оплачивает свой газ.
- [x] **1. Границы одного расчёта** — при первом `CalculateRewards()` фиксируются текущий пул и состав событий текущей серии. Новые комиссии, mint, ремонты и поломки после этого относятся к следующему расчёту.
- [x] **2. Claim во время незавершённого расчёта** — разрешён. Пользователь получает только уже рассчитанную сумму; необработанные отрезки будут доступны после завершения соответствующей серии `CalculateRewards()`.
- [x] **3. Ремонт как событие** — создаётся запись с точным временем ремонта. Все расчёты до этой записи выполняются без машины; после записи машина участвует в расчётах. Задним числом доход не начисляется. Если серия `CalculateRewards()` уже началась, событие относится к следующей серии.
- [x] **4. Нет активных машин** — комиссии остаются в пуле. Когда появляется одна активная машина, она получает весь доступный пул при следующем `CalculateRewards()`.
- [x] **5. Обработка очереди** — `CalculateRewards()` может вызвать любой адрес, но компенсации газа и бонуса нет. Вызывающий полностью оплачивает транзакцию самостоятельно.
- [x] **6. Ремонт до полной поломки** — разрешён. Если осталось 2 часа, стоимость считается за 4 дня 22 часа; после ремонта прочность становится 5 дней, старая запись окончания становится неактуальной, новая запись добавляется в очередь.
- [x] **7. Частота `CollectFees()`** — backend вызывает сбор при достижении заданной минимальной суммы комиссий. Порог суммы будет задан отдельной настройкой.

## Чек-лист

- [x] **1. Контракт $FARE** — простой ERC-20 без дополнительных требований к tokenomics-логике. Комиссии направляются на смарт-контракт; предусмотрена возможность сжигания `$FARE`.
-
  **Зафиксировано:** отдельные `mint`, `pause` и upgradeability для токена пока не требуются. Механика комиссий реализуется контрактами парка/Uniswap hook, а не усложнением самого ERC-20.
- [x] **2. NFT-машины** — используем ERC-721. NFT хранит владение машиной, а `weight`, пробег, число смен и состояние ТО хранятся в отдельном контракте парка/стейкинга.
- [x] **3. Стажёрская программа** — на стажёров выделяется отдельный пул в размере **5%** комиссий; основной пул парка получает **45%**. Публичное кодовое слово публикуется в Twitter и намеренно доступно для поиска пользователями.
  - Пользователь вводит слово во frontend.
  - Backend проверяет актуальность слова и выдаёт персональный подписанный claim-вoucher.
  - Smart contract проверяет подпись backend, адрес кошелька, `nonce`, срок действия, `chainId` и адрес контракта.
  - Само кодовое слово в blockchain не передаётся и on-chain не хранится.
  - Ваучер нельзя повторно использовать или применить к другому кошельку.
  - Боты могут находить публичные слова; это допустимо, поскольку стажёры финансируются отдельным пулом и не затрагивают основную экономику.
- [x] **3a. Длительность стажёрской машины** — **6 часов**.
- [x] **3b. Формат стажёрской машины** — виртуальная машина без NFT. Smart contract хранит временную запись кошелька с датами выдачи/окончания, `lastClaim`, весом и статусом активности. Такая машина не продаётся и не переводится.
- [x] **3c. Стажёрский пул** — стажёры делят только фактически накопленные 5% комиссий. Фиксированной выплаты и гарантированного дохода нет; при большом количестве стажёров доля каждого уменьшается.
- [x] **3d. Перенос накопленного дохода при продаже NFT** — накопленная claimable-доля принадлежит самой NFT и переходит новому владельцу вместе с ней. Свежесминченная NFT не получает комиссии, накопленные до её минта.
- [x] **4. Активность машины** — отдельной кнопки «На смену» нет. Машина активна от mint или ремонта до `activeUntil`. `CalculateRewards()` permissionless обрабатывает события активности, а NFT можно передавать в любое время вместе со всем её состоянием и незабранным доходом.
- [x] **5. Границы расчётного пула** — при начале серии `CalculateRewards()` текущие доступные активы фиксируются отдельно. Серия распределяет их по временным отрезкам и активным весам; новые поступления сохраняются для следующей серии.
- [x] **6. Учёт комиссий Uniswap** — используем отдельный `FeeCollector`. Uniswap v4 hook отправляет комиссии в него, а `FeeCollector` распределяет средства по направлениям: касса парка, buyback/burn, корзина акций и операционные средства.
- [x] **7. Покупка stock-токенов** — используем отдельную permissionless-функцию `buyBasket()`. Любой адрес может вызвать покупку корзины; контракт проверяет whitelist токенов, допустимый slippage и минимальные суммы сделки.
- [x] **8. Whitelist stock-токенов** — используем жёсткий whitelist адресов, заданный при деплое. Разрешённые адреса не меняются обычной операционной логикой контракта.
- [x] **9. Оплата газа** — пользователь сам оплачивает газ в ETH за `claim`, активацию эпохи и остальные транзакции. Gasless через ERC-4337 пока не используем.
- [x] **10. Выплаты** — распределение выполняет `CalculateRewards()` без переводов тысячам владельцев, используя доход одного веса. `Claim(tokenId)` может вызвать только текущий владелец и получает рассчитанный доход одной NFT. Максимальное количество NFT — 9500; перебора и массовых переводов в `Claim()` нет.
- [x] **11. Округления** — остатки от округления переносятся в следующую эпоху и не сжигаются.
- [x] **12. Прочность машины и ремонт** — отказываемся от смен. Максимальная прочность каждой машины равна `X = 5 дней`, хранимых в секундах.
  - Прочность определяется временем от mint или последнего ремонта; `Claim()` на неё не влияет.
  - Контракт хранит `activeUntil`, а оставшееся время вычисляет относительно текущего `block.timestamp`.
  - Если прочность закончилась, машина больше ничего не получает, пока её не починят.
  - Для расчёта ремонта контракт хранит историю рассчитанных временных отрезков минимум за последние `X` дней.
  - Ремонт всегда восстанавливает полные 5 дней, оплачивается в `$FARE`; уплаченные токены сжигаются.
  - Стоимость ремонта рассчитывается по доходу активных машин: сумма дохода за нужный отрезок времени делится на сумму их весов, затем результат умножается на вес ремонтируемой машины.
  - Пример с отрезками `5ч, 3ч, 12ч, 24ч, 48ч, 24ч, 20ч` требует отдельной проверки арифметики и точного алгоритма выбора отрезков.
- [x] **13. История расчётных отрезков и окно `X` дней** — храним общую историю рассчитанных временных отрезков в кольцевом буфере минимум за последние `X = 5 дней`. В каждой записи есть время начала, время окончания, доход на один вес и общая сумма, начисленная всем машинам за этот отрезок. Отдельную историю отрезков для каждой NFT не создаём: её активные границы, вес и единый `claimable` хранятся в состоянии самой машины.
- [x] **14. Точная формула ремонта** — ремонт всегда восстанавливает машину до полной прочности `X = 5 дней`. Стоимость считается только за недостающий срок. Выплаты за период, когда машина была сломана, задним числом не начисляются. Арифметику примера нужно проверить при детализации формулы.
- [x] **15. Активные машины** — активна любая сминченная NFT с прочностью больше нуля. Машина с нулевой прочностью исключается из суммы весов; после ремонта сразу возвращается в активный вес.
- [x] **16. Ремонт и начисления** — ремонт действует с точного времени транзакции. Машина возвращается в активный вес с этой секунды, но рассчитанный доход становится доступен для `Claim()` только после того, как `CalculateRewards()` дойдёт до события ремонта. Выплаты за период простоя задним числом не начисляются.
- [x] **17. Emergency-функции** — используем одну глобальную `pause`, rescue случайно отправленных токенов и замену внешних адресов (например, Uniswap, FeeCollector и других зависимостей). Экономические параметры и whitelist отдельно не меняем. Во время паузы блокируются все изменяющие состояние операции проекта, включая mint, transfer NFT, ремонт, стажёрскую активацию, `CollectFees()`, `CalculateRewards()` и `Claim()`; чтение данных остаётся доступным.
- [x] **18. Upgradeability** — логика контрактов immutable после деплоя. Разрешено менять только адреса внешних зависимостей через выбранные emergency-функции.
- [x] **19. Smart contracts: основной стек** — Solidity + OpenZeppelin + Foundry. Foundry используем для компиляции, тестов, локальной сети, gas-анализа и deployment. Hardhat пока не добавляем.
- [x] **20. Frontend** — React + Vite + TypeScript. Интерфейс остаётся минимальным и общается со smart contracts через Web3-библиотеку.
- [x] **21. Backend** — Node.js/TypeScript + MongoDB для индексации событий, истории и статистики. Blockchain остаётся источником истины, MongoDB используется как быстрый read-слой.
- [x] **22. Blockchain data/indexer** — собственный indexer на Node.js/TypeScript + MongoDB, с периодической сверкой и восстановлением по blockchain. Blockchain остаётся источником истины.
- [x] **23. Wallet и Web3-интеграция** — используем `viem` + `wagmi`. `wagmi` отвечает за подключение кошелька и React-состояние, `viem` — за чтение и вызов smart contracts.
- [x] **24. Deployment и окружения** — используем Foundry scripts и `.env` для параметров сетей. CI запускает тесты и сборку, но не деплоит. Публикация в testnet/mainnet выполняется вручную и требует отдельного разрешения.
- [x] **25. Тестовая среда** — используем Anvil и mocks для быстрых локальных тестов, затем выполняем smoke-тест в Robinhood testnet перед публикацией. В mainnet не деплоим без отдельного разрешения.

## Дополнительная модель начислений

- [x] **26. Lazy accounting выплат** — используем общий доход на единицу веса. Для каждой NFT храним время последнего расчёта, время окончания текущей активности, вес и один накопленный `claimable`-баланс. При `Claim()` выполняется небольшой расчёт только для этой NFT.
- [x] **27. Динамическая активность машин** — используем одну хронологическую очередь событий без перебора 9500 NFT. При mint или ремонте в очередь добавляется событие будущего окончания прочности. `CalculateRewards()` перебирает эту же очередь по времени: каждое событие задаёт границу очередного временного отрезка, доход за отрезок рассчитывается с действующим на нём `totalActiveWeight`, после чего машина добавляется в активный вес или исключается из него. При ремонте старое событие окончания не удаляется физически, а становится неактуальным через версию состояния машины.
- [x] **28. Публичные функции выплат** — используем три функции:
  - `CollectFees()` — забирает комиссии на наши контракты, закупает stock-токены и пополняет соответствующие пулы. Вызывать может любой адрес; backend делает это автоматически.
  - `CalculateRewards()` — продвигает очередь расчётов максимум на 20 событий за одну транзакцию. Вызывать может любой адрес; backend последовательно обрабатывает очередь.
  - `Claim()` — пользователь забирает доход своей машины.
- [x] **29. Способ начисления всем машинам** — `CalculateRewards()` сохраняет рассчитанные временные отрезки и увеличивает общий счётчик дохода одного веса. У каждой NFT записываются показания этого счётчика в начале и конце её активного периода, вес, уже выплаченная граница и единый `claimable`. При `Claim()` контракт вычитает начальное показание из конечного и умножает разницу на вес, поэтому не перебирает всю историю отрезков и все NFT.
- [x] **30. Новые комиссии во время расчёта** — комиссии, собранные после начала серии `CalculateRewards()`, относятся к следующей серии и не меняют зафиксированный текущий пул.
- [x] **31. Что считается одним событием** — одно изменение состояния одной NFT (`MINT`, `REPAIR` или `EXPIRE`) является отдельным событием и отдельным шагом лимита `CalculateRewards()`. События никогда не объединяются, даже если несколько машин изменились в одну секунду или в соседние секунды. При одинаковом времени промежуток между событиями равен нулю, но состояние каждой NFT обновляется отдельно. Специального приоритета нет: при равном времени события идут в порядке добавления. Курсор хранит пару `timestamp + eventNumber`, чтобы следующая транзакция не повторяла обработанные и не пропускала оставшиеся события той же секунды.
- [x] **32. Claim во время незавершённой очереди** — разрешён; пользователь получает только уже рассчитанный доход, а оставшаяся часть станет доступна после продвижения очереди.
- [x] **33. Несколько `CollectFees()` подряд** — все собранные комиссии складываются в общий текущий пул. В момент `CalculateRewards()` распределяется весь баланс, который есть в пуле; время отдельных `CollectFees()` не учитывается.
- [x] **34. Ошибка покупки stock-токенов** — ошибка покупки одного токена не отменяет успешно выполненные направления `CollectFees()`. Непотраченная доля остаётся закреплённой за конкретным stock-направлением в `stockReserve` и повторно используется при следующей попытке. Перенаправлять её в другие пулы или отключать slippage-защиту нельзя.
- [x] **35. Расчёт при пустом пуле** — `CalculateRewards()` продвигает очередь даже при нулевом пуле. События обрабатываются, активный вес обновляется, а пройденные временные отрезки фиксируются с нулевым доходом и не участвуют в распределении денег, поступивших позже. Выбрано как наиболее простое поведение без отдельного расчётного курсора.
- [x] **36. Награда за служебные функции** — компенсации и бонуса нет. Вызывающий `CollectFees()` или `CalculateRewards()` самостоятельно оплачивает газ в ETH.
- [x] **37. Возвращение активной машины** — если в пуле накопились деньги, а затем снова появилась только одна активная машина, она получает весь доступный пул при следующем `CalculateRewards()`.
- [x] **38. Ремонт как событие расчёта** — при ремонте старая запись окончания прочности становится неактуальной, а в очередь добавляется новая запись окончания через 5 дней. При mint добавляется аналогичная запись начала активности/окончания прочности. При обработке события машина добавляется или исключается из активного расчёта.
- [x] **39. Границы одного расчёта** — в начале серии `CalculateRewards()` фиксируются текущий пул, время начала и время окончания расчёта. Новые комиссии и события, появившиеся после начала серии, относятся к следующей серии.
- [x] **40. Начисление без перебора машин** — вместо записи дохода в каждую активную NFT обновляем общий счётчик дохода одного веса. Конкретная NFT получает сумму по разнице показаний за свой активный период при `Claim()` или при обработке события изменения её состояния.
- [x] **41. Размер шага расчёта** — один вызов `CalculateRewards()` обрабатывает максимум 20 отдельных NFT-событий. Перед деплоем это значение проверяется gas-тестом; при необходимости код корректируется до публикации immutable-контракта.
- [x] **42. Физический баланс и расчётный остаток** — физические деньги остаются на контракте до пользовательского `Claim`, но уже обработанная часть пула резервируется внутренним учётом и не участвует в следующих расчётах.
- [x] **43. Новые комиссии во время частичного расчёта** — контракт отдельно хранит зафиксированный остаток текущей серии и поступления следующей серии. `CollectFees()` во время незавершённого расчёта не увеличивает текущий остаток; после завершения новые поступления становятся пулом следующей серии.
- [x] **44. Автоматическое закрытие периода при ремонте** — транзакция ремонта сразу записывает событие с точным временем и новый срок окончания через 5 дней, даже если расчётная очередь отстаёт. Когда `CalculateRewards()` хронологически доходит до этого события, он закрывает старый период, добавляет его рассчитанный доход в `claimable` NFT и фиксирует текущее показание дохода одного веса как начало нового периода. До обработки события пользователь может забрать только ранее рассчитанный доход. Старые периоды отдельно не хранятся.
- [x] **45. Повторный ремонт при отставшей очереди** — повторные ремонты разрешены, даже если `CalculateRewards()` ещё не обработал предыдущее событие ремонта. Каждое событие сохраняется с точным временем и обрабатывается по хронологии. Каждый ремонт восстанавливает прочность до 5 дней, оплачивается только фактически недостающая на этот момент прочность и делает предыдущую будущую поломку неактуальной. Итоговая поломка назначается через 5 дней после последнего ремонта.
- [x] **46. Право на ремонт после transfer** — ремонт может вызвать только текущий владелец NFT. Стандартные ERC-721 approvals позволяют передавать NFT, но не дают оператору права ремонтировать машину. Прочность, очередь событий и накопленный доход принадлежат самой NFT и переходят новому владельцу вместе с ней.
- [x] **47. Цена ремонта при отставшей очереди** — ремонт не ждёт, пока расчёт догонит фактическое время. Стоимость определяется по последнему доступному полностью рассчитанному окну нужной длительности, которое заканчивается на текущем курсоре `CalculateRewards()`. Frontend показывает время, по состоянию на которое рассчитана цена. Нерассчитанные отрезки в цену текущего ремонта не входят.
- [x] **48. Недостаточная история для цены ремонта** — если рассчитанная история короче недостающего срока прочности, цена считается только по реально доступной истории без пропорционального увеличения. Недостающий отрезок не оценивается искусственно. Если рассчитанной истории ещё нет, стоимость ремонта равна нулю.
- [x] **49. Stock-токены в распределении** — в расчётную серию попадают только фактически купленные stock-токены, уже находящиеся на контракте. Неудавшаяся покупка остаётся денежным `stockReserve` и не создаёт долг перед NFT. После успешной повторной покупки токены поступают в следующую серию и распределяются только с этого момента.
- [x] **50. Хранение прочности** — для машины хранится точное время поломки `activeUntil`, а не отдельно уменьшаемое количество оставшихся секунд. Оставшаяся прочность вычисляется как `max(activeUntil - currentTime, 0)`. `Claim()` не меняет `activeUntil`; ремонт устанавливает `activeUntil = repairTime + 5 дней` и создаёт соответствующее событие поломки.
- [x] **51. Точная граница поломки** — активный период хранится как полуоткрытый интервал `[activeFrom, activeUntil)`. Машина активна только при `timestamp < activeUntil`; при `timestamp >= activeUntil` она уже сломана. Так машина работает ровно 5 дней без дополнительной секунды и двойного начисления на границе.
- [x] **52. Начало дохода после mint** — новая NFT начинает участвовать с точного времени минта и не получает доход за более ранние отрезки. Она может делить уже находящийся в контракте нераспределённый пул за время после минта, потому что время поступления отдельных комиссий не учитывается. Если расчётная серия началась до минта, событие относится к следующей серии.
- [x] **53. Transfer NFT и расчётная очередь** — передача NFT не создаёт событие расчёта, потому что вес, `activeUntil` и участие машины не меняются. `claimable`, текущий активный период, прочность и очередь будущих событий принадлежат NFT и переходят новому владельцу. После transfer только новый владелец может вызвать `Claim()` или ремонт; результат конкурирующих действий определяется обычным порядком транзакций в blockchain.
- [x] **54. Размер одного Claim** — `Claim(tokenId)` обрабатывает ровно одну NFT и доступен только её текущему владельцу. Контракт не обходит все NFT кошелька и не предоставляет `ClaimAll()` в первой версии. Во frontend каждая машина имеет отдельную кнопку получения дохода.
- [x] **55. Атомарность Claim** — выплата одной NFT выполняется целиком. Если перевод любого начисленного актива завершается ошибкой, вся транзакция откатывается: ранее выполненные в ней переводы отменяются, а `claimable` и контрольные значения NFT не изменяются. Частичные выплаты и отдельные долги по токенам не создаются.
- [x] **56. Область аварийной паузы** — одна глобальная пауза блокирует все операции, изменяющие состояние, включая transfer NFT и вывод уже начисленного дохода. Состояние, активы и позиции очередей сохраняются; после `unpause` работа продолжается с прежнего места.
- [x] **57. Округление разных активов** — расчёты выполняются с повышенной внутренней точностью, а фактические переводы округляются вниз до минимальной единицы конкретного ERC-20. Нераспределимый остаток каждого актива хранится отдельно и добавляется в следующую серию того же актива. Остатки `$FARE` и разных stock-токенов не смешиваются, не сжигаются и не перенаправляются.
- [x] **58. Одновременные CalculateRewards** — вызывающий не передаёт ожидаемый курсор. Каждая транзакция читает актуальную позицию очереди в момент исполнения и обрабатывает следующие максимум 20 событий, поэтому последовательно включённые в блок вызовы продолжают друг друга без двойного начисления. Награды за вызов нет независимо от количества обработанных событий.
- [x] **59. Оплата permissionless-вызовов** — протокол не компенсирует газ и не выплачивает бонусы за `CollectFees()` или `CalculateRewards()`. Backend выполняет их за свой счёт; любой другой адрес может сделать то же самое за собственный ETH.
