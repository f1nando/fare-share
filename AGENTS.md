# Правила старта и разработки нового проекта

Этот файл является главным рабочим соглашением для нового проекта. Его следует скопировать в корень нового репозитория как `AGENTS.md` или использовать как основу для такого файла.

Если другие документы противоречат этому файлу, приоритет имеет этот файл, если пользователь явно не дал другое указание в текущей задаче.

## 1. Главный приоритет

Главная цель проекта — максимальная скорость разработки при приемлемой надёжности и производительности.

Порядок приоритетов:

1. Быстро получить работающий результат.
2. Сохранить простоту кода и возможность быстро его менять.
3. Обеспечить приемлемую надёжность для реального использования.
4. Обеспечить достаточную, измеримую производительность.
5. Добавлять дополнительную инфраструктуру и гарантии только при доказанной необходимости.

Не следует заранее строить решение для гипотетических масштабов, отказов и нагрузок. Не следует усложнять проект ради формальной «enterprise-ready» архитектуры.

Предпочтительно простое решение, которое можно быстро проверить и изменить. Более сложное решение допускается только если простое уже создаёт конкретную проблему.

## 2. База данных: только MongoDB

MongoDB является единственной базой данных проекта от начала разработки до production.

По умолчанию запрещено:

- использовать PostgreSQL, MySQL, MariaDB, SQLite и другие SQL-базы;
- добавлять SQL-драйверы, SQL ORM, SQL query builders и SQL migration frameworks;
- создавать SQL-схемы, таблицы, SQL-миграции или временный SQL-контур для тестов;
- предлагать переход на SQL «для надёжности», «на будущее» или «для масштабирования»;
- поднимать SQL-сервисы локально, в CI или в production;
- тратить время на сравнение MongoDB с SQL, если пользователь отдельно об этом не попросил.

SQL можно использовать только после прямой и однозначной просьбы пользователя включить SQL. Такая просьба должна относиться к конкретной задаче и не меняет постоянное правило MongoDB-only автоматически.

Если библиотека или шаблон по умолчанию предлагает SQL, нужно выбрать MongoDB-совместимую альтернативу.

### 2.1. Работа с MongoDB

Использовать MongoDB непосредственно или через тонкий, понятный слой доступа к данным. Не создавать тяжёлую абстракцию, имитирующую реляционную БД.

Правила моделирования:

- хранить связанные данные вместе, когда они обычно читаются и изменяются вместе;
- использовать ссылки между коллекциями только когда встраивание приводит к явному дублированию, неограниченному росту документа или неудобным обновлениям;
- не нормализовывать данные по привычке из SQL;
- создавать индексы под реальные запросы, а не полный набор предполагаемых запросов;
- уникальные индексы использовать для действительно уникальных бизнес-идентификаторов;
- TTL-индексы использовать для временных данных, сессий, nonce, кэша и истекающих задач;
- транзакции MongoDB использовать только там, где несколько записей действительно должны измениться атомарно;
- для большинства операций предпочитать атомарное изменение одного документа;
- использовать идемпотентные операции для платежей, webhook, очередей и повторных запросов;
- включать MongoDB schema validation только для критичных коллекций или когда отсутствие валидации уже приводит к ошибкам;
- не вводить отдельный data migration framework заранее.

Изменения структуры документов по умолчанию должны быть обратно совместимыми:

- новые поля имеют безопасные значения по умолчанию;
- код временно понимает старую и новую форму документа;
- небольшой backfill выполняется отдельным коротким скриптом только когда он реально нужен;
- массовое преобразование всей базы не запускается из-за обычной правки кода;
- удаление поддержки старого формата выполняется после того, как необходимость подтверждена.

## 3. Скорость важнее максимальной полноты проверок

Проверки должны быть пропорциональны реальному риску изменения. Нельзя проверять всю систему после каждой локальной правки.

Целевые бюджеты:

| Тип изменения | Обычный набор проверок | Целевое время |
|---|---|---:|
| Текст, иконка, цвет, отступ, простая кнопка | синтаксис или сборка затронутого frontend | до 1 минуты |
| Изолированная UI-логика | связанные unit/component tests и сборка | до 2 минут |
| Frontend flow | связанные тесты и один browser smoke | до 3 минут |
| Один API endpoint | тесты только этого endpoint и затронутых функций | до 3 минут |
| Локальная бизнес-логика | focused unit tests | до 5 минут |
| Изменение модели MongoDB или индекса | focused repository/integration tests | до 5 минут |
| Большая связанная функция | затронутые unit/integration tests | до 10 минут |
| Release candidate | полный согласованный regression suite | запускается отдельно |

Если обычная локальная проверка превышает бюджет, нужно остановиться, определить причину и сократить проверку. Не следует молча ждать 20–40 минут.

Долгий полный прогон допустим только:

- по прямой просьбе пользователя;
- перед production-релизом, если пользователь попросил подготовить или выполнить релиз;
- после изменения общей инфраструктуры, затрагивающей большую часть проекта;
- когда focused tests не способны проверить реальный риск, и это кратко объяснено.

## 4. Матрица проверок по области изменения

### Только тексты, стили и статические assets

Запускать только самое быстрое из доступного:

- проверку синтаксиса;
- focused lint для изменённого файла;
- frontend build, если без него нельзя подтвердить корректность.

Не запускать:

- backend tests;
- MongoDB integration tests;
- database setup;
- browser suite целиком;
- production smoke;
- deployment pipeline.

### Frontend-компонент или клиентская логика

Запускать:

- тесты изменённого компонента или модуля;
- typecheck затронутого workspace, если он быстрый;
- одну сборку;
- один browser smoke только если изменился пользовательский сценарий.

Backend и MongoDB не запускать, если API-контракт не менялся. Для данных использовать fixtures, mocks или локальные handlers.

### API или backend-функция

Запускать:

- unit tests изменённой функции;
- focused тест конкретного endpoint;
- минимальный integration test с MongoDB только если затронут persistence.

Не запускать frontend suite, если контракт и поведение UI не менялись.

### MongoDB repository, коллекция или индекс

Запускать:

- focused tests соответствующего repository;
- минимальный integration test на одной локальной или ephemeral MongoDB;
- проверку создания конкретного нового индекса, если индекс менялся.

Не пересоздавать всю production-подобную базу и не импортировать полный production snapshot.

### Общий контракт или сквозной сценарий

Запускать только тесты затронутого сквозного сценария. Полный E2E suite не является значением по умолчанию.

### Deployment и release pipeline

Проверять отдельно от обычной разработки. Изменение приложения не означает автоматическую проверку или запуск deployment pipeline.

## 5. Режимы работы

В проекте существуют четыре независимых режима.

### `dev`

Режим по умолчанию:

- локальные изменения;
- быстрые focused tests;
- mocks и fixtures;
- без production-доступа;
- без полного regression;
- без публикации.

### `verify`

Используется для расширенной локальной проверки завершённой функции:

- связанные unit tests;
- связанные integration tests;
- сборка;
- один или несколько целевых E2E smoke.

`verify` не запускается автоматически для минимальной правки.

### `release`

Используется только по прямому запросу подготовить релиз:

- полный согласованный набор проверок;
- создание воспроизводимого артефакта, если это нужно проекту;
- проверка конфигурации и совместимости;
- release notes только по существенным изменениям.

### `deploy`

Используется только по прямому разрешению пользователя на публикацию:

- production deployment;
- необходимые smoke checks;
- контролируемый rollback или fix-forward;
- краткий итог без огромного отчёта.

Запросы «реализуй», «исправь», «измени», «проверь» и «закоммить» не означают разрешение на публикацию или deployment.

## 6. Frontend должен разрабатываться независимо

Frontend должен:

- запускаться и собираться без реального backend;
- использовать fixtures или mock API для повседневной разработки;
- иметь отдельные быстрые команды lint, test и build;
- позволять проверить страницу или компонент без базы данных;
- не требовать полного E2E для изменения текста или стилей;
- не требовать production snapshot;
- не блокироваться из-за недоступности MongoDB, если текущая задача не связана с данными.

Нормальный цикл простой UI-правки:

```text
изменение → focused frontend check → при необходимости build → локальный commit
```

Нормальный цикл изменения frontend flow:

```text
изменение → связанные tests → один browser smoke → локальный commit
```

## 7. Backend и MongoDB должны запускаться быстро

Локальная разработка не должна каждый раз заново устанавливать или конфигурировать MongoDB.

Предпочтительно:

- переиспользовать уже запущенную локальную MongoDB;
- иметь одну короткую команду запуска dev-окружения;
- использовать небольшие fixtures;
- очищать только коллекции, принадлежащие конкретному тесту;
- использовать уникальный database name для параллельных тестов;
- мокать внешние сервисы;
- не копировать production database для обычной разработки;
- не выполнять полный backfill перед тестом;
- не создавать индексы повторно в каждом unit test.

Если integration tests требуют заметного времени, unit tests должны использовать простой in-memory fake repository с тем же минимальным интерфейсом. Fake не должен превращаться во вторую реализацию MongoDB.

## 8. Архитектура: минимально достаточная

По умолчанию использовать модульный монолит.

Не добавлять без конкретной необходимости:

- микросервисы;
- Kubernetes;
- service mesh;
- Kafka или сложную event platform;
- несколько баз данных;
- CQRS и event sourcing;
- универсальный repository framework;
- сложный dependency injection container;
- многослойную абстракцию вокруг MongoDB;
- отдельный data warehouse;
- распределённые блокировки;
- преждевременное шардирование;
- сложную observability-платформу.

Разделять код по понятным функциям продукта, а не создавать большое число слоёв ради архитектурной чистоты.

Предпочтительная минимальная структура:

```text
src/
  frontend/
  server/
  features/
  db/
  shared/
tests/
scripts/
```

Конкретная структура может отличаться, если стек диктует более простой вариант.

## 9. Приемлемая надёжность

Надёжность должна защищать пользователя и данные от наиболее вероятных ошибок, но не должна превращать каждую правку в длительный аудит.

Обязательны там, где применимо:

- базовая валидация внешнего ввода;
- авторизация для закрытых действий;
- уникальные индексы для уникальных идентификаторов;
- идемпотентность платежей, webhook и повторяемых jobs;
- явная обработка ошибок внешних API;
- timeout для сетевых запросов;
- ограниченные retries с backoff;
- секреты только через environment или secret storage;
- резервное копирование production MongoDB;
- минимальное логирование ошибок без секретов и персональных payload;
- одна или несколько проверок критичного happy path.

Не обязательны по умолчанию:

- формальное доказательство всех инвариантов;
- проверка каждого незатронутого endpoint;
- полная копия production для каждого теста;
- отчёт с сотнями SHA и PID после каждой правки;
- zero-downtime deploy для раннего продукта;
- multi-region failover;
- стопроцентное покрытие тестами;
- сложная цепочка approvals для обычных изменений.

Для необратимых денежных операций уровень проверки может быть выше, но он должен касаться только соответствующего денежного сценария.

## 10. Производительность: сначала измерение

Не оптимизировать гипотетическую нагрузку.

Порядок работы:

1. Реализовать простой вариант.
2. Измерить реальный медленный сценарий.
3. Найти конкретный bottleneck.
4. Исправить его минимальным изменением.
5. Повторно измерить тот же сценарий.

Предпочитать:

- подходящий MongoDB index;
- projection только нужных полей;
- pagination и ограниченный `limit`;
- batch operations вместо большого количества последовательных запросов;
- кэш только для измеримо горячих чтений;
- background job только для действительно долгой работы;
- простые rate limits на дорогие публичные endpoints.

Не добавлять Redis только «на будущее». Он допускается после измерения и только если MongoDB и in-process cache не решают конкретную проблему.

## 11. Тестовая стратегия

Цель тестов — быстро обнаруживать вероятные поломки, а не доказывать абсолютную корректность всей системы.

Рекомендуемая пирамида:

- много коротких unit tests для важной логики;
- несколько focused integration tests для MongoDB и внешних контрактов;
- мало E2E tests для главных пользовательских сценариев;
- ручная визуальная проверка только когда изменение действительно визуальное.

Правила:

- сначала запускать один наиболее релевантный тест;
- после исправления не расширять прогон без причины;
- не запускать весь suite из осторожности;
- flaky test изолировать или исправлять, а не перезапускать много раз;
- тест не должен зависеть от порядка запуска;
- внешнюю сеть в обычных tests мокать;
- production endpoints не использовать как тестовую среду;
- snapshots использовать умеренно, только когда они действительно помогают;
- при отсутствии теста для маленькой безопасной правки допустимы build и краткая ручная проверка.

Полный suite должен запускаться в CI или перед релизом, а не быть обязательной частью каждой итерации.

## 12. Git и локальные коммиты

После завершённой логической правки создавать отдельный локальный commit, если репозиторий использует Git.

Перед commit:

- проверить только затронутую область;
- просмотреть diff;
- добавить в index только свои файлы;
- не использовать слепой `git add .` в загрязнённом рабочем дереве;
- не включать логи, screenshots, dumps, credentials, backups и временные artifacts.

Если рабочее дерево содержит чужие изменения, не изменять и не коммитить их. При необходимости использовать отдельную ветку или worktree.

Локальный commit не разрешает:

- `git push`;
- создание или обновление PR;
- GitHub release;
- production deployment.

Эти действия выполняются только по прямой просьбе пользователя.

## 13. Экономия времени и токенов агента

Агент должен действовать компактно и целенаправленно.

Запрещается без необходимости:

- читать весь репозиторий перед маленькой правкой;
- читать все документы проекта, если достаточно одного связанного файла;
- повторять полные результаты уже выполненных проверок;
- выводить длинные логи в чат;
- создавать большой отчёт после каждого изменения;
- перечислять все неизменившиеся сервисы, PID, SHA и routes;
- выполнять одинаковую проверку несколькими способами;
- запускать subagents для простой последовательной задачи;
- исследовать альтернативные технологии, если решение уже задано;
- превращать локальную задачу в production audit.

Следует:

- сначала найти конкретный затронутый файл;
- читать только нужные фрагменты;
- использовать focused search;
- переиспользовать существующие scripts и fixtures;
- сообщать короткие промежуточные обновления только при длительной работе;
- в финале указывать результат, изменённые файлы, выполненные проверки и известные ограничения;
- хранить долгую историю релизов вне постоянных инструкций.

## 14. Документация

Постоянная документация должна быть короткой и актуальной.

Рекомендуемые файлы:

- `AGENTS.md` — только действующие правила работы;
- `README.md` — запуск и краткое описание продукта;
- `ARCHITECTURE.md` — только текущая архитектура и важные решения;
- `DEPLOY.md` — короткая процедура публикации;
- `CHANGELOG.md` — существенные изменения релизов.

Не добавлять в `AGENTS.md` полный журнал всех прошлых deployment. Старые PID, пути release, временные SHA, промежуточные ошибки и подробные доказательства должны находиться в release notes или git history, а не загружаться в контекст каждой новой задачи.

Документацию обновлять только если изменение делает существующую инструкцию неправильной или добавляет важное постоянное правило.

## 15. Внешние сервисы и зависимости

Выбирать сервисы, которые сокращают время разработки.

По умолчанию допустимы managed services, если они:

- быстро подключаются;
- имеют понятную цену;
- не создают критичный vendor lock-in для ранней версии;
- заменяют существенный объём собственного infrastructure-кода.

Каждая новая dependency должна решать текущую задачу. Не добавлять библиотеку ради функции, которую можно понятно реализовать несколькими строками без риска.

Не обновлять все dependencies во время несвязанной задачи.

## 16. Безопасность без бюрократии

Минимальные обязательные правила:

- не коммитить secrets;
- не выводить secrets в логи и чат;
- проверять права на серверных endpoints;
- считать клиент недоверенным;
- валидировать входные данные на границе системы;
- ограничивать размер request body и uploads;
- использовать безопасные cookie и HTTPS в production;
- не выполнять необратимые внешние действия в тестах;
- перед удалением production-данных точно проверять target.

Не нужно проводить полный security audit после каждой правки. Расширенная security-проверка выполняется отдельно для auth, платежей, загрузок файлов, публичных API и перед важным релизом.

## 17. Поведение при неопределённости

Если есть несколько примерно равноценных вариантов, выбирать самый простой и быстрый обратимый вариант.

Не задавать пользователю вопрос, если можно сделать безопасное и легко изменяемое предположение. Кратко сообщить о предположении в результате.

Остановиться и спросить пользователя нужно только если выбор:

- существенно меняет продукт;
- создаёт заметные расходы;
- приводит к необратимому внешнему действию;
- требует credentials или новых прав;
- включает SQL вопреки MongoDB-only правилу;
- означает публикацию или production deployment.

## 18. Критерий готовности обычной задачи

Обычная задача считается завершённой, когда:

- запрошенное поведение реализовано;
- diff не содержит случайных изменений;
- выполнена самая короткая достаточная проверка;
- нет известной очевидной ошибки в затронутом сценарии;
- создан локальный commit, если это требуется правилами репозитория;
- пользователь получил краткий итог.

Для завершения обычной задачи не требуется:

- полный regression;
- production-like environment;
- длительный load test;
- полный browser matrix;
- проверка всех API;
- публикация;
- release report;
- доказательство неизменности всей остальной системы.

## 19. Критерий готовности релиза

Релиз проверяется отдельно и только после явного перехода в режим `release`.

Минимальный release checklist:

- приложение собирается;
- проходят критичные tests;
- проходят главные happy-path smoke scenarios;
- configuration для целевого окружения проверена;
- MongoDB indexes и необходимые обратно совместимые изменения готовы;
- существует понятный способ отката к предыдущей версии приложения или быстрого fix-forward;
- deployment явно разрешён пользователем.

Не расширять checklist автоматически. Каждый дополнительный gate должен предотвращать уже известный существенный риск и оправдывать своё время.

## 20. Команды проекта

Новый проект должен стремиться к следующему простому интерфейсу команд:

```text
dev                 запустить локальную разработку
test <target>       запустить focused tests
test:changed        проверить только изменённые области
build               собрать приложение
verify              расширенно проверить текущую функцию
test:all            запустить полный suite вручную
release             подготовить release candidate
deploy              выполнить отдельно разрешённую публикацию
```

Названия могут соответствовать используемому package manager, но смысл команд должен сохраняться.

`test` не должен неявно запускать полный suite. `build` не должен запускать integration tests. `dev` не должен пересоздавать базу. `deploy` не должен быть частью обычной проверки.

## 21. Автоматический выбор проверок

Желательно добавить короткий script `test:changed`, который выбирает проверки по `git diff`.

Пример правил:

```text
frontend styles/text/assets  → frontend lint/build
frontend component          → component tests/build
frontend flow               → related tests/one browser smoke
server pure logic           → related unit tests
API handler                 → endpoint tests
MongoDB repository          → related repository integration tests
MongoDB index definition    → index check and related query test
shared contract             → affected frontend and backend contract tests
deployment files            → deployment script tests only
```

Если script не уверен, он должен выбрать небольшой расширенный набор, а не весь проект.

## 22. Явные антицели

Проект не стремится:

- использовать SQL;
- достигнуть максимальной теоретической надёжности;
- иметь сложную инфраструктуру с первого дня;
- проходить полный regression после каждой строки;
- поддерживать все гипотетические масштабы;
- обеспечивать нулевой downtime любой ценой;
- создавать исчерпывающие отчёты о каждой правке;
- максимизировать test coverage как самостоятельную метрику;
- копировать процессы крупных компаний без их реальных требований;
- тратить десятки минут на проверку минутной UI-правки.

## 23. Правило пересмотра

Эти правила меняются на основании реальной боли и измерений.

Новый обязательный процесс добавляется только если:

1. произошла конкретная существенная проблема или выявлен повторяемый риск;
2. понятно, как новый процесс предотвращает именно эту проблему;
3. стоимость процесса соразмерна риску;
4. процесс применяется только к затронутому классу изменений;
5. по возможности процесс автоматизирован.

Если проверка регулярно занимает больше времени, чем сама разработка, её нужно упростить, сузить или перенести в release/CI-контур.

## 24. Короткая инструкция агенту перед каждой задачей

Перед началом работы:

1. Определи минимальную область изменения.
2. Не подключай SQL ни в каком виде.
3. Не запускай database tests, если данные не затронуты.
4. Выбери самый короткий достаточный test.
5. Не запускай полный suite без отдельной причины.
6. Не публикуй и не деплой без прямой просьбы.
7. Не трогай чужие изменения в рабочем дереве.
8. Если проверка становится долгой, остановись и сузь её.
9. Зафиксируй завершённую логическую правку отдельным локальным commit.
10. Сообщи результат кратко и конкретно.

Итоговый принцип проекта:

> MongoDB от начала до конца. Простая архитектура. Быстрые focused checks. Полные проверки только перед релизом. Никакой инфраструктуры и сложности без измеримой необходимости.

## 25. Режим чата-координатора

Для проекта должен существовать один постоянный главный чат, который работает как координатор, диспетчер задач и единственная точка сборки релизов.

Рекомендуемое название чата:

```text
[COORDINATOR] Название проекта — задачи и релизы
```

Первое сообщение пользователя для активации режима:

```text
РЕЖИМ: КООРДИНАТОР ПРОЕКТА

Ты являешься главным координатором этого проекта. Принимай мои задачи в непрерывную очередь, присваивай им номера, выбирай подходящий способ выполнения и модель, запускай исполнителей, принимай их результаты, интегрируй готовые коммиты и управляй релизами. Ни один исполнитель не может пушить или деплоить. Публикацией управляешь только ты по моему прямому или заранее условному разрешению.
```

После активации координатор должен ответить заметной постоянной меткой:

```text
[COORDINATOR ACTIVE]
Project: <название>
Queue: ready
Release authority: coordinator only
```

Эта роль сохраняется для всего чата. Координатор не должен превращаться в обычного независимого исполнителя и терять состояние очереди.

### 25.1. Назначение координатора

Координатор отвечает за:

- приём новых задач пользователя;
- присвоение каждой задаче стабильного ID;
- выявление зависимостей и конфликтующих файлов;
- определение порядка выполнения;
- выбор модели и reasoning effort под конкретную задачу;
- решение, выполнить задачу самому или делегировать исполнителю;
- создание изолированного worktree для параллельного исполнителя, если это нужно;
- контроль focused-проверок;
- приём только завершённых результатов с commit SHA;
- интеграцию готовых изменений в единую версию;
- ведение состава следующего релиза;
- выполнение немедленного или условного deployment по разрешению пользователя;
- информирование пользователя о готовности принимать следующую задачу.

Только координатор может:

- определять итоговый release scope;
- интегрировать commits исполнителей;
- пушить общую ветку;
- создавать или обновлять PR;
- создавать release candidate;
- запускать deployment;
- объявлять production-версию опубликованной.

### 25.2. Конвейер входящих задач

Пользователь может отправлять задачи координатору последовательно, не ожидая полного завершения предыдущей задачи. Каждое новое сообщение с изменением продукта считается новой входящей задачей, если пользователь явно не указал, что оно уточняет или заменяет существующую.

После получения задачи координатор должен быстро:

1. Присвоить ID вида `T-001`, `T-002`, `T-003`.
2. Дать ей короткое название.
3. Определить затронутую область.
4. Определить зависимости от других задач.
5. Оценить риск конфликтов.
6. Выбрать модель и reasoning effort.
7. Поставить задачу в очередь или немедленно запустить её.
8. Кратко подтвердить приём.

Формат подтверждения:

```text
[QUEUED T-014] Исправить мобильное меню
Priority: normal
Depends on: none
Execution: worker / fast model / low reasoning
Queue position: 3
```

Если сообщение уточняет уже существующую задачу, координатор не создаёт дубликат, а отвечает:

```text
[UPDATED T-014]
Добавлено требование: закрывать меню после перехода.
```

Если пользователь отменяет задачу:

```text
[CANCELLED T-014]
```

Если отменённая задача уже имеет commit, координатор не удаляет историю и не выполняет destructive Git-команды. Он исключает commit из интеграции либо создаёт отдельный безопасный revert, если commit уже был интегрирован.

### 25.3. Статусы задач

Использовать ограниченный набор статусов:

```text
INBOX       задача принята, но ещё не разобрана
QUEUED      задача разобрана и ожидает запуска
RUNNING     исполнитель работает
BLOCKED     требуется решение пользователя или внешнее условие
READY       реализация и focused-проверка завершены, commit получен
INTEGRATED  commit включён в общую интеграционную версию
RELEASED    изменение опубликовано в production
CANCELLED   задача отменена и не должна попасть в релиз
FAILED      текущая попытка не завершена; задача требует нового решения
```

`READY` без commit SHA запрещён. Исключение допускается только для задач, не изменяющих файлы и внешнее состояние, например для консультации или анализа.

### 25.4. Последовательность и параллельность

По умолчанию координатор обрабатывает задачи последовательно. Это основной режим максимальной предсказуемости:

```text
T-001 → commit → integration
T-002 → commit → integration
T-003 → commit → integration
```

Последовательная обработка обязательна, когда задачи:

- меняют один и тот же файл или компонент;
- зависят друг от друга;
- меняют общую модель данных;
- меняют один пользовательский сценарий;
- используют одну и ту же нестабильную локальную среду;
- должны войти в production строго в определённом порядке.

Параллельная работа разрешена, когда она действительно сокращает время и задачи независимы.

Для параллельного изменения кода каждый исполнитель должен получить отдельный Git worktree и собственную временную ветку. Два исполнителя не должны одновременно редактировать одну общую рабочую папку.

Read-only исследования, просмотр документации, анализ логов и ревью могут выполняться параллельно без worktree, если они не меняют файлы.

Координатор должен ограничивать число одновременных исполнителей. По умолчанию достаточно:

- одного write-исполнителя;
- до двух дополнительных read-only исполнителей;
- большего числа только по явной выгоде и при отсутствии конфликтов.

### 25.5. Выбор модели для задачи

Координатор выбирает модель после краткого анализа задачи, а не использует самую дорогую модель для всего подряд.

Сначала определяется класс задачи:

| Класс | Примеры | Предпочтение |
|---|---|---|
| Быстрая механическая | текст, CSS, rename, небольшой docs update, понятная правка одного файла | самая быстрая доступная coding-модель, low reasoning |
| Обычная реализация | компонент, endpoint, небольшая функция, focused bugfix | сбалансированная coding-модель, low или medium reasoning |
| Исследование | поиск владельца кода, чтение большого числа файлов, анализ логов | быстрая модель для чтения и синтеза, low или medium reasoning |
| Сложная реализация | несколько подсистем, неоднозначные требования, race conditions | сильная coding-модель, medium или high reasoning |
| Критическая | auth, платежи, необратимые операции, release integration, deployment recovery | наиболее надёжная доступная модель, high reasoning |

Текущие названия моделей могут меняться, поэтому основное правило основано на классах возможностей. Координатор использует только модели, реально доступные в текущей среде.

Если доступны актуальные модели семейства Codex/OpenAI, ориентировочное распределение может быть таким:

- быстрые и хорошо ограниченные задачи — быстрая модель уровня `luna`, low reasoning;
- исследование, чтение и обычные рабочие задачи — модель уровня `terra`, low или medium reasoning;
- сложная многошаговая реализация — основная сильная coding-модель, medium или high reasoning;
- сложная интеграция, архитектурное решение или рискованный релиз — наиболее сильная доступная модель, high reasoning.

Координатор не обязан сообщать подробное обоснование модели для каждой мелкой задачи. Достаточно показывать выбранный класс в подтверждении очереди. Если выбор существенно влияет на время или стоимость, кратко объяснить его.

Если задача оказалась сложнее первоначальной оценки, координатор может:

- повысить reasoning effort;
- передать задачу более сильной модели;
- разделить её на подзадачи;
- вернуть неудачную попытку в очередь с новым планом.

Не следует продолжать много раз одной и той же слабой моделью, если она явно не справляется.

### 25.6. Контракт с исполнителем

Каждый исполнитель получает ограниченную задачу с явным результатом:

```text
Task: T-014 — исправить мобильное меню.
Scope: только frontend navigation.
Do not: не менять API, MongoDB, deployment и чужие файлы.
Validation: component test и frontend build.
Finish: создать отдельный локальный commit и вернуть SHA, список файлов и краткий итог.
Publishing: запрещено.
```

Исполнитель должен вернуть:

```text
READY T-014
commit: abc1234
files:
  - src/frontend/Menu.tsx
  - src/frontend/menu.css
checks:
  - menu component test PASS
  - frontend build PASS
notes: none
```

Координатор не принимает результат как `READY`, если:

- нет commit SHA;
- в commit попали посторонние изменения;
- не выполнена минимальная относящаяся проверка;
- реализация не соответствует scope;
- исполнитель самостоятельно публиковал или деплоил изменения.

### 25.7. Готовность принимать следующую задачу

Координатор не должен требовать от пользователя ждать завершения текущей задачи, чтобы сообщить следующую.

После постановки задачи в работу координатор сохраняет возможность принимать новые сообщения. Новые задачи добавляются в очередь и не должны автоматически отменять текущую, если пользователь прямо не написал `замени`, `останови`, `отмени` или эквивалентное указание.

После каждого существенного перехода координатор сообщает короткий статус:

```text
[T-014 RUNNING] Исполнитель запущен.
[QUEUE READY] Можно присылать следующую задачу.
```

После завершения:

```text
[T-014 READY] commit abc1234
[NEXT] Запускаю T-015.
[QUEUE READY] Можно присылать новые задачи.
```

Не нужно публиковать длинный отчёт после каждой задачи. Полная сводка выводится по запросу пользователя или перед релизом.

### 25.8. Состояние очереди

Координатор должен поддерживать компактное состояние:

```text
RUNNING
- T-014 Mobile menu

QUEUED
- T-015 Deposit button text
- T-016 Portfolio empty state

READY
- T-011 Header spacing — abc1234
- T-012 API validation — def5678

INTEGRATED
- T-009, T-010

DEPLOY CONDITION
- none
```

По команде `покажи очередь` координатор возвращает эту сводку без лишних логов.

Для долгого проекта состояние должно периодически сохраняться в репозитории в компактной машинно-читаемой или Markdown-форме. Не использовать один постоянно конфликтующий файл для параллельной записи исполнителями. Очередь изменяет только координатор; исполнители возвращают результаты координатору.

### 25.9. Интеграция готовых задач

Координатор интегрирует только задачи со статусом `READY`.

Перед интеграцией он проверяет:

- commit существует;
- commit содержит только заявленные файлы и изменения;
- зависимости задачи уже интегрированы;
- commit не отменён;
- нет очевидного конфликта с более новым изменением;
- focused checks относятся к реальному изменению.

После интеграции задача получает статус `INTEGRATED`. Наличие commit в отдельном worktree или ветке ещё не означает включение в релиз.

### 25.10. Команда «задеплой сейчас»

Фраза пользователя `задеплой сейчас` является прямым разрешением координатору подготовить и выполнить deployment текущего готового состава.

По умолчанию в такой релиз входят все задачи со статусом `INTEGRATED`, которые ещё не были опубликованы. Задачи `RUNNING`, `QUEUED`, `BLOCKED`, `FAILED` и неинтегрированные `READY` не включаются.

Перед deployment координатор показывает короткий freeze состава:

```text
[DEPLOY NOW]
Included: T-009, T-010, T-011
Excluded as not ready: T-012, T-013
Release candidate: <SHA>
```

Если пользователь перечислил конкретные задачи, release scope ограничивается ими:

```text
Задеплой сейчас T-009 и T-011.
```

Координатор не должен молча включать другие готовые правки в такой ограниченный релиз.

После freeze запрещено добавлять новые изменения в тот же release candidate. Новая задача относится к следующему релизу, если пользователь явно не отменил freeze и не изменил scope.

### 25.11. Условный deployment

Пользователь может заранее разрешить deployment после готовности определённых задач:

```text
Задеплой, когда будут готовы T-014, T-015 и T-016.
```

Это считается прямым условным разрешением на deployment и не требует повторного подтверждения после выполнения условия.

Координатор должен зафиксировать:

```text
[DEPLOY CONDITION ARMED]
Required: T-014, T-015, T-016
Scope: only these tasks and their declared dependencies
Action: integrate → focused combined check → release candidate → deploy
```

Правила условного deployment:

- deployment начинается только когда все перечисленные задачи имеют статус `READY` или `INTEGRATED`;
- обязательные зависимости этих задач также должны быть готовы;
- в релиз не попадают более поздние задачи, если они явно не добавлены в условие;
- отсутствие одной задачи блокирует только этот deployment, но не обработку остальной очереди;
- при `FAILED` или `BLOCKED` координатор сообщает проблему и не публикует неполный состав;
- если требуется новое внешнее разрешение, credentials, платёж или необратимое действие вне ранее указанного scope, координатор останавливается и спрашивает пользователя;
- условие можно изменить командами `добавь T-017 в deployment`, `убери T-015 из deployment` или `отмени deployment`;
- после успешного deployment условие автоматически снимается;
- один и тот же release candidate не деплоится повторно без причины.

Можно задавать условие по смысловым названиям до присвоения ID:

```text
Задеплой, когда будут готовы мобильное меню, новая кнопка депозита и пустое состояние портфеля.
```

Координатор обязан связать названия с конкретными ID и вернуть пользователю точный список для устранения неоднозначности.

### 25.12. Новые задачи при активном условии deployment

Если пользователь добавляет новые задачи после установки условия deployment, координатор продолжает принимать их в очередь.

Новая задача не добавляется в уже вооружённое условие автоматически.

Пример:

```text
Condition: deploy after T-014, T-015
New task: T-016
```

После готовности `T-014` и `T-015` координатор публикует их, даже если `T-016` ещё выполняется. `T-016` попадёт в следующий релиз, если пользователь не добавил её в текущее условие.

Если `T-016` меняет те же файлы и технически конфликтует с релизом, координатор должен либо:

- удержать её в очереди до freeze текущего релиза;
- выполнять её в отдельном worktree;
- кратко сообщить о необходимости изменить порядок.

### 25.13. Защита от неполного релиза

Перед любым push или deployment координатор обязан проверить release manifest:

```text
release SHA
included task IDs
source commit каждого task
declared dependencies
focused check каждого task
combined smoke result
explicit deployment authorization or active condition
```

Если задача названа пользователем как обязательная, но её commit не является предком release SHA, deployment должен завершиться до публикации с ошибкой `REQUIRED TASK NOT INCLUDED`.

Запрещено:

- деплоить из worktree исполнителя;
- деплоить dirty working tree;
- собирать артефакт до окончательного freeze;
- заменять release SHA после проверки;
- публиковать часть обязательного условного scope;
- считать наличие ветки доказательством включения изменения;
- разрешать исполнителю самостоятельно пушить свою неполную версию.

### 25.14. Восстановление после ошибки исполнителя

Если исполнитель завершился без результата, координатор:

1. Сохраняет задачу и её требования.
2. Проверяет, не остался ли полезный безопасный commit.
3. Не интегрирует незавершённое состояние.
4. Уточняет scope или выбирает другую модель.
5. Запускает новую ограниченную попытку.

Не следует терять задачу, создавать несколько неразличимых дублей или публиковать частичный результат ради освобождения очереди.

### 25.15. Короткие команды пользователя

Координатор должен понимать следующие команды:

```text
покажи очередь
покажи готовые
покажи состав следующего релиза
приоритет T-014 высокий
поставь T-014 после T-018
останови T-014
отмени T-014
добавь это к T-014
задеплой сейчас
задеплой сейчас T-014 и T-015
задеплой когда будут готовы T-014, T-015 и T-016
добавь T-017 в deployment
убери T-015 из deployment
отмени deployment
не деплой, только собери release candidate
```

### 25.16. Главный принцип координации

> Пользователь свободно отправляет задачи в один чат как на конвейер. Координатор сохраняет очередь, выбирает подходящую модель, последовательно или безопасно параллельно запускает исполнителей, принимает только commit-bound результаты, собирает одну полную версию и единолично управляет релизом по немедленной или заранее заданной условной команде пользователя.
